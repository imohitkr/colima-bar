# Security policy

## Supported versions

Only the [latest release](https://github.com/imohitkr/colima-bar/releases/latest) gets security fixes. If you use an older version, update before you report a problem.

## Report a vulnerability

Do not open a public issue, discussion or pull request for a vulnerability.

Report it privately through GitHub:

1. Open the [Security tab](https://github.com/imohitkr/colima-bar/security) of this repository.
2. Click **Report a vulnerability**.
3. Fill in the form and submit it.

Include this information:

- The ColimaBar version and the macOS version.
- The output of `colima version`.
- What an attacker can do, and what access the attacker needs first.
- Steps to reproduce the problem, or a proof of concept.
- Relevant lines from `~/.cache/colima-bar/ctl.log`. Remove secrets before you send them.

## What to expect

- The maintainer acknowledges the report within one week.
- This is a volunteer project. There is no fixed time for a fix.
- The maintainer keeps you informed and tells you before the fix is public.
- If you agree, the security advisory credits you for the report.

## Scope

These notes describe how ColimaBar works. They help you decide if a problem is a vulnerability.

- **The ColimaBar socket and the profile sockets.** ColimaBar listens on the ColimaBar socket (`~/.cache/colima-bar/docker.sock`). It also listens on one profile socket for each docker profile (`~/.cache/colima-bar/profiles/PROFILE.sock`). Each socket has mode `0600`. Each socket folder has mode `0700`. Only your macOS user can connect. A way for another local user to connect is a vulnerability.
- **The `colimabar` command.** It runs as your user. `status`, `doctor` and `diagnostics` only read, and `diagnostics` never overwrites a file. `--profile` must pass `ProfileName.isValid` and reaches `colima-ctl.sh` only through the environment. The app writes `~/.cache/colima-bar/app-status.json` with mode `0600`. A way to make the command change a setting, create a VM, or run something other than `colima-ctl.sh` is a vulnerability.
- **Docker daemon access.** Access to a socket of the Docker daemon is equal to root access inside the VM. The ColimaBar socket and each profile socket give the same access as the Colima socket of their profile, and no more. Any process that runs as your user can already use the Colima socket. Thus this access alone is not a vulnerability.
- **Docker routes.** ColimaBar sets these routes:
  - `DOCKER_HOST` with `launchctl setenv`.
  - `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` with `launchctl setenv`. All apps that you open from the Dock or Finder get it.
  - The docker context `colimabar`, and one docker context `colimabar-PROFILE` for each profile socket. ColimaBar changes only the `colimabar-PROFILE` contexts whose description starts with "ColimaBar".
  - `docker.host` in `~/.testcontainers.properties`.
  - The optional `/var/run/docker.sock` symlink, only after you click **Link (admin)**.

  If ColimaBar changes a route that points to a different daemon, report it.
- **`colima-ctl.sh`.** The app bundle contains this script. It runs VM actions and changes `colima.yaml`. For the VM settings, ColimaBar writes the new file to `~/.cache/colima-bar/colima.PROFILE.yaml.new` (mode `0600`, no symlink). `vm-config` accepts only a regular file at that path, and only if the SHA-256 of `colima.yaml` has not changed. It saves a copy in `colima.PROFILE.yaml.bak`. Injection through a profile name or a setting is a vulnerability. So is a way to write a file other than the `colima.yaml` of the profile.
- **Network checks.** ColimaBar connects to published ports on `127.0.0.1` and sends no data. It runs `colima ssh` with a script built only from port numbers, and looks up `registry-1.docker.io`. It reads the Mac DNS setup with no permission. Notifications hold no address or domain. A check that sends data, starts a VM, or passes container text to a shell is a vulnerability.
- **`colimabar://` links.** Any app or web page can open a link. A link can only open the dashboard or Doctor, or start, stop or restart an existing VM. It never returns data, writes a file or opens a panel. Its only parameter is a profile name that must pass `ProfileName.isValid` and be in `colima list`. While **Ask before a link starts, stops or restarts Colima** is on, ColimaBar asks first. The setting is not in the settings file. A link that runs a command, reads data, creates a VM, or skips the question while the setting is on is a vulnerability.
- **Inspect values.** The Inspect page reads the environment, labels and command of a container. It keeps these values in memory only. It hides values by the name of the key or by the shape of the value, until you click the eye. A way to send an Inspect value to a log, a notification or the diagnostics file is a vulnerability.
- **Compose actions.** The project menu runs `docker compose pull`, `up -d` and `down` with the name and the paths from the labels of a container. Any client of the Docker daemon can set these labels. ColimaBar and `colima-ctl.sh` check them: a name from a fixed list of characters, absolute paths with no `..`, files that exist, and an argument list with no shell. A way to make a compose action run a path or an option that these checks reject is a vulnerability.
- **Image update check.** It is off by default. It uses only the Docker API on the own socket of the profile, so it never starts the VM. It calls `GET /distribution/REF/json` and `POST /images/create` with an escaped reference. It sends no `X-Registry-Auth` header, so the daemon contacts a registry without a sign-in. The log holds counts only, never an image reference. A notification for a failed pull holds the reference and the message of the daemon, cut to 120 characters. A debug run contacts no registry and pulls no image. A way to make the check start a VM, send a sign-in, write a reference to the log, or contact a registry in a debug run or while the setting is off is a vulnerability.
- **Debug shell.** **Debug shell** runs `docker run --rm -it --name colimabar-debug-ID12 --pid container:ID --network container:ID --cap-add SYS_PTRACE IMAGE` on the profile socket. It never starts a stopped VM. ID must be 64 hex characters. IMAGE comes from the hidden key `debugShellImage` and must start with a lowercase letter or a digit, then use only letters, digits and `. _ / : @ -`. ColimaBar and `colima-ctl.sh` both check them. A way to add another flag, use `--privileged`, or pass a name or an option as ID or IMAGE is a vulnerability.
- **Volume backup.** **Back Up…** and **Restore from Backup…** use the Docker API on the own socket of the profile, so they never start the VM. They create a helper container from an image that ColimaBar builds on the Mac and loads with `POST /images/load`. The container never starts. A backup file has the mode `0600`. ColimaBar opens it with `O_EXCL` and `O_NOFOLLOW` and never follows a symlink. A cancel or an error removes it. A restore reads the whole file first and refuses an absolute path, a `..` part, a name outside `v/`, a hard link to a target outside `v/`, a device and a file that ends early. A backup file holds the data of the volume in plain form: protect it like the volume. ColimaBar deletes the helper container with `force` and never removes a volume with it. It deletes a volume only after you click **Replace All Files**, or for a new volume that a failed restore created. A way to make a restore write outside the chosen volume, to make a backup file readable by other users, or to make ColimaBar delete another container or volume is a vulnerability.
- **VM type change.** **Change and Recreate…** runs `colima-ctl.sh vm-recreate VMTYPE MOUNTTYPE`. The script accepts only the pairs of a fixed list (`recreate_pair_ok`), so no path or free text comes from the app. It builds the copies of `colima.yaml` itself in `~/.cache/colima-bar` (mode `0700`) and stops the VM (`colima stop`), deletes it with `colima delete --force` (never `--data`) and starts it again. It ignores SIGPIPE, so it can finish after ColimaBar quits. ColimaBar makes the backup folder with `mkdir` (mode `0700`, it fails if the name exists) and writes all files with mode `0600` through `PrivateFileWriter`, never through a link. `images.tar` goes to `POST /images/load` only if its SHA-256 equals the value in the journal, so a swapped file is refused. The volume restore keeps the full `TarFileScan` check. The journal `~/.cache/colima-bar/recreate.PROFILE.json` is read with a check of the format, the version, the profile name and the file names. It holds names and image references, no secrets and no environment. Docker messages are cut to 120 characters. Notifications show the name of the folder, not its path.
- **Cleanup.** **Empty…** runs `sudo -n truncate -c -s 0` on one json log file in the VM through `colima ssh`. The script checks that the container ID has 64 lowercase hex characters and builds the path itself. **Return Free Space** runs `sudo -n fstrim -av` in the VM. The weekly cleanup (off by default) runs `docker image prune` and `docker builder prune` on the profile socket. These actions never start a stopped VM and never remove a volume. A way to make **Empty…** change a file other than the json log of a container, or to make the weekly cleanup remove a volume or a used image, is a vulnerability.
- **Container domains.** The proxy binds only `127.0.0.1` and `::1`, and it connects only to `127.0.0.1` (or `::1` for a port that is published there only) and a published host port from the Docker list. It routes by the `Host` header and answers a host outside `.localhost` and the custom suffix with a page that has no route list. It never starts a VM. Other users of the Mac can reach the loopback ports, as they reach any published port. A way to make the proxy bind a non-loopback address, connect anywhere other than loopback, start a VM, or show a route list to a request with a foreign `Host` is a vulnerability.
- **Local certificate authority.** HTTPS (off by default) makes a P-256 CA with name constraints. It may sign only DNS names under `localhost` and under the custom suffix, if you set one. It excludes every IP address. Its only extended key usage is server authentication, and macOS trusts it for this user and for the SSL policy only. Its certificate is in the login keychain. Its key is a file with the mode `0600` in a folder with the mode `0700` (`~/Library/Application Support/ColimaBar/domains`) that is not in backups. The key is never a keychain item. Any process of your user can read the key file, as it can read any file of yours. A stolen key can sign only websites under `.localhost` and the custom suffix. A change of the suffix replaces the CA, and ColimaBar deletes the old key. The server certificates (30 days) stay in memory. The TLS identities of the leaves exist in memory only: ColimaBar imports each one from a PKCS#12 blob with a random password, with no keychain involved. Older versions kept a temporary file keychain in `~/Library/Caches/com.imohitkr.ColimaBar/tls`, and the next launch deletes its leftover files. A password dialog follows only a click. A debug run makes no CA and changes no keychain or trust setting. Turning HTTPS off, or the uninstall script, deletes the key file and asks macOS to remove the certificate and its trust setting. If you cancel that dialog, the certificate stays in the keychain without effect. ColimaBar makes a server certificate only for the name of a running container (and its subdomains). Another name gets the certificate of `localhost`. A certificate that this CA signs outside the constraints, a key in a keychain, or a key file that other users can read is a vulnerability.
- **Custom suffix.** The DNS server (off by default) binds only `127.0.0.1` on a high UDP port and answers only for names under the suffix. ColimaBar writes `/etc/resolver/SUFFIX` only with an administrator prompt (`osascript` with administrator privileges). The file has the marker line, `nameserver 127.0.0.1` and `port N`, with N from 20000 to 32767. It has the mode `0644` and the owner `root:wheel`. The shell runs `mkdir -p /etc/resolver`, writes a temporary file `/etc/resolver/.SUFFIX.colimabar-tmp` and renames it with `mv -f`. It removes the temporary file if a step fails. The prompt shows when you apply, change or repair the suffix, or turn it off. It never shows at launch, at quit or when you turn the master switch off. ColimaBar removes only files that have its marker line on the first line and are regular files, never a link or another tool's file. It writes the new file before it removes the old one. The uninstall script runs `sudo rm -f` on the marked files (and marked temporary files) in `/etc/resolver` only. The root shell gets only a suffix that passes the check (`test`, or one or two labels before `test`, `internal` or `home.arpa`), a fixed folder, a fixed marker and an integer, all quoted. A way to make ColimaBar write or remove another file in `/etc`, or answer for names outside the suffix, is a vulnerability.
- **Import Settings…** reads a JSON file that you choose. A setting from such a file that changes behavior beyond its documented values is a vulnerability.
- **Code signing.** ColimaBar has an ad-hoc signature. Apple does not notarize it. The signature only shows that the app is not damaged. It does not show who built it.
- **Download integrity.** GitHub Actions signs a build provenance attestation for each release file. To check a download, follow [Verify a download](docs/install.md#verify-a-download). If a release file fails this check, report it.
- **In-app update.** After you confirm, ColimaBar downloads `ColimaBar.zip` of the exact release tag from github.com (it never uses `latest` or a URL from the API). It follows redirects only to https hosts of GitHub (`github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`). It accepts only an immutable release, and it compares the size and the SHA-256 digest of the file with the values of the GitHub API. If `gh` 2.68 or later is installed and logged in, it also runs `gh attestation verify` with the flags of the installer. The dialog says if `gh` cannot run the check. Only then does the update go on with the digest check. If the dialog promised the check and `gh` cannot run it later, the update stops. It unpacks the zip into a private folder, and accepts only one entry, `ColimaBar.app`, with a valid signature, the code identifier `com.imohitkr.ColimaBar`, the version of the release and a newer version than the running one. It replaces the bundle by rename only, and restarts. The trust rests on TLS and GitHub. The digest catches damage, a cut-off download and a changed copy on the CDN. It does not catch a hijacked GitHub account or a changed CI workflow. Immutable releases keep the files of a tag. The attestation (when `gh` runs) shows that `ci.yml` of this repository built the file from the tag on a GitHub-hosted runner. The ad-hoc signature shows integrity only. Homebrew is stronger: the cask holds the SHA-256 in a separate repository, and the tap checks the attestation. A way to make ColimaBar install a file that fails one of these checks is a vulnerability. A test build with the update test hook is not a release: report a release binary that contains the hook (the string `COLIMABAR_UPDATE_BASE`).

Problems in Colima, Lima or Docker are out of scope. Report them to those projects.
