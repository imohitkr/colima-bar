# Architecture

This document describes the high-level design of ColimaBar. Read it before you make a large change. For build, test and pull request steps, read [CONTRIBUTING.md](CONTRIBUTING.md). For the user guides, read [docs/](docs/README.md).

## Bird's-eye view

ColimaBar is a menu bar app for [Colima](https://github.com/abiosoft/colima). It does three jobs:

1. **The dashboard.** It shows the VM and its containers, and runs actions on them.
2. **Auto-start.** It runs a proxy on a unix socket, the stable socket. All docker clients use that socket. While the VM is down, the first real docker request starts Colima. Each docker profile also has its own proxy socket, the profile socket, which starts that profile.
3. **Auto-stop.** It can stop the VM of each running profile after an idle time.

It also takes `colimabar://` links, a keyboard shortcut and the `colimabar` command.

ColimaBar is one native process. It uses Swift 6.4, SwiftPM and Apple frameworks only (AppKit, SwiftUI, Observation, UserNotifications, ServiceManagement, IOKit, CryptoKit, Security for the local certificate authority of HTTPS, Network for the proxy of container domains, SystemConfiguration for the network watch, Carbon HIToolbox for the keyboard shortcut; `notify` is part of libSystem). It has no third-party dependencies. It runs on Apple silicon with macOS 15 or later.

ColimaBar gets its data from these sources:

- **The Docker Engine API on the unix socket** of the selected profile. For auto-stop and for starts, the model also calls the sockets of the other running profiles. The docker CLI and Portainer use the same transport. `/events` streams changes. `/containers/{id}/stats?stream=1` streams samples for each container, but only while a dashboard is on screen. `docker stats --no-stream` blocks for about 2 seconds on each call, and the stream does not.
- **The `colima` CLI.** Colima has no API. Thus ColimaBar reads VM data from `colima list -j`, and the driver and mount type from `colima status -j`.
- **`colima ssh` probes.** The port and DNS checks run a short script in the VM. It is built only from port numbers.
- **SystemConfiguration.** It reports changes of the DNS setup of the Mac (network changes), which start the DNS check.
- **`scripts/colima-ctl.sh`.** The app bundle contains this script. VM actions, actions that ask for confirmation and changes to `colima.yaml` go through it. Container start, stop and restart calls go directly to the API. Compose shortcuts and the debug shell also go through it. They use the profile socket and take no VM lock.

## Code map

Sources live in `Sources/ColimaBar/`, in one folder per area. Each file holds one type, or one type and its small private helpers. The file has the name of the type. An extension file has the name `Type+Topic.swift`. Tests in `Tests/ColimaBarTests/` use the same folders.

### `App/`

`AppDelegate` owns the menu bar icon, the popover, the dashboard window, the right-click menu (`showMenu()`) and the debug flags. It also makes sure that only one instance runs. `AppDelegate+Relaunch` restarts the app after an update replaced its bundle (`relaunchIfUpdated(reveal:)` in `AppDelegate`). `MainMenu` adds the Edit and Window menus. `AppDelegate+Links` receives and handles `colimabar://` links, with `AppLink` (the parser), `AppLinkPolicy` (the gates, the texts) and `LinkInbox` (the queue). `AppDelegate+Shortcut` runs the dashboard shortcut (`toggleDashboard()`, with the pure `ShortcutAction` table in its own file). `StatusItemPlacement` decides if the icon can anchor the popover. `ScreenGeometry` is the plain value of a screen that it reads. `Snapshot` renders the debug screenshots.

### `CLI/`

The `colimabar` command. See [Command line](#command-line). `CLIParser` reads the arguments into a `CLIRequest` (no library). `CLIRunner` runs a request, and `CLIRunner+Actions` runs `start`, `stop`, `restart` and `open`. `CLIExit` holds the exit codes and `CLIHelp` the help text. `CLIStatus` is the answer of `status` (JSON and text), and `CLIStatusProbe` makes its inputs with reads only. `CLIDoctorReport` is the output of `doctor`. `CLIDiagnosticsPath` decides the file of `diagnostics`. `CLIProfile` picks the profile. `CLIOutput` is stdout and stderr.

### `Model/`

`ColimaModel` is the `@Observable` single source of truth for the dashboard, auto-start and auto-stop. It runs the heartbeat, starts the VM of a profile for a proxy (`wakeForProxy(profile:)`), checks for idle time (`checkIdle()` for the selected profile, `checkOtherProfilesIdle()` for the others) and runs the profile actions (`createProfile`, `deleteProfile`, `startProfile`, `stopProfile`).

- `ColimaModel+Rules`: static rules, for example when to hide the icon and how often the heartbeat runs.
- `ColimaModel+Inspect`: reads one container for the Inspect page (`inspect(id:)`: `GET /containers/{id}/json` and, once, `GET /images/{id}/json` for the digests). `ColimaModel+Compose` runs the Compose shortcuts. `ContainerDetail` is the value that the page shows. `ComposeProject` reads the `com.docker.compose.*` labels and checks the name and the paths. `ComposeVerb` names pull, up and down. `EnvMask` and `EnvEntry` decide which environment values the page hides. `MountPathMap` maps a path in the VM back to the Mac. `PortLink` builds the `localhost` link of a published port. `DebugShell` checks the container ID and the image name of a debug shell, and `ColimaModel+DebugShell` runs it.
- `ColimaModel+Events`: which `/events` messages cause which refresh, and which ones go to `RemovedLogKeeper`.
- `ColimaModel+StartDetection`: finds a `colima start` that already runs, so ColimaBar does not start a second one.
- `ColimaModel+Settings`: reads the user settings for an export, and applies imported settings through the normal setters.
- `KeyCombo`: a keyboard shortcut as a pure value (Carbon key code and modifier mask). It parses and writes the spec string, checks the rules, and makes the symbols and the spoken text. `KeyCombo+Layout` adds the text with the key name of the keyboard layout.
- `SettingsTransfer`: the settings file format (JSON with a format name and a version), its checks and the import plan.
- Cleanup, see [Cleanup](#cleanup): `CleanupReport` and `CleanupItem` (the rows of the Cleanup page, from the df decode), `LogFileSizes` (the VM command that lists the json log files, and its parser), `DiskImageSize` (the disk image files of a profile and their sizes), `DiskTrim` (the `fstrim` output and the notification text), `PruneSchedule` (the rules of the weekly cleanup) and `ColimaModel+Cleanup` (the model side).
- `DiskShrink`: the rules and the warning text for a smaller disk, with the line about volume backups.
- Volume backup, see [Volume backup](#volume-backup): `VolumeBackupRunner` (the Docker calls), `VolumeBackupBatch` (the loop over the volumes of a backup), `VolumeRestoreFlow` (the order of a restore), `ColimaModel+VolumeBackup` (the model side: state, notifications, clean-up), `VolumeTransfer` (the state of the progress strip), `HelperImage` (the image, the labels and the container body), `TarScanner`, `TarHeader` and `TarFileScan` (the tar checks), `VolumeBackupMeta` (the first entry of a file), `VolumeRestorePlan` (the rules for a target volume), `VolumeBackupName` (file and volume names) and `TransferProgress`.
- `VMConfig`: the VM settings in the `colima.yaml` of the selected profile (`ColimaModel.config`), and the values that the settings show (`VMConfig.shown`). For a stopped VM, `colima list` shows the values of the last start, not the file. Memory is a decimal number of GiB, as in Colima: `memory: 2.5` is 2.5 GiB. CPU and disk are whole numbers.
- `VMSettings`, `VMSettingsChange`, `VMSettingsCheck`, `VMMount`, `VMSettingsFailure`, `ColimaModel+VMSettings`: the advanced VM settings, see [VM settings](#vm-settings). `VMSettings.read` gives the values of `colima.yaml` and which fields ColimaBar cannot edit. `VMSettingsChange` holds only the fields to write. `VMSettingsCheck` checks a change (pure). `ColimaModel.vmSettings` is the read of the selected profile.
- `AutoStopRule`: the idle rule for one profile (it uses `SuspendingClock`), the idle time for the power state (`limit`), the stop time and which other profiles auto-stop checks.
- `AfterSleepCheck`: which profiles the check after a system sleep covers, its ping delays and its notification texts.
- `ClockDrift`: measures the clock of a VM against the Mac, and builds the command that fixes it.
- `ProfileName`: the name rules of `colima-ctl.sh`, and the stricter rules for a new profile.
- `NewProfileForm`: the values and checks of the New Profile form (with the VM type and the mount type).
- VM type change, see [VM type change](#vm-type-change): `VMTypeRules` (the valid pairs, the defaults and the QEMU check), `VMRecreatePlan` (what to back up, the space check and the confirmation text), `VMRecreateFlow` (the order of the steps, with injected steps), `VMRecreateJournal` (the record on disk and what the notice says), `VMRecreateProgress` (the strip), `ImageArchiveRunner` (image save and load) and `ColimaModel+VMRecreate` (the model side).
- `ProfileDelete`: when a delete is refused, its warning text and the profile to select after it.
- `CtlAction`: the actions of `colima-ctl.sh`.
- Diagnostics, see [Diagnostics](#diagnostics): `DiagnosticsPart`, `DiagnosticsSection`, `DiagnosticsBundle` (the file text and its limits), `Redactor`, `ColimaConfigSummary`, `CrashReportDigest` and `ColimaModel+Diagnostics`. Doctor, see [Doctor](#doctor): `DoctorCheck` (the twelve checks), `DoctorResult` (a status, a detail and an optional `DoctorFix`), `DoctorFix`, `DoctorInputs` (everything the checks read), `DoctorRules`, `DoctorRules+Docker` and `DoctorRules+Network` (the pure rules: inputs in, results out), `DoctorReport` (the results of one run, its summary and its plain text), `ColimaModel+Doctor` (`runDoctor()`, `applyFix(_:)`, `repairProfile()`, `currentDoctorReport`, `doctorHint`). The upgrade guard has `VersionChange`, `GoodStarts`, `UpgradeGuard` and `ColimaModel+Upgrade`, see [Upgrade guard](#upgrade-guard). The network checks have `PortHealth`, `DNSHealth`, `MacDNSConfig` and `ColimaModel+NetworkHealth`, see [Network health](#network-health). The parsers and rules have their own types: `ToolVersions`, `ShellStartupScan`, `DockerConfig`, `StaleLimaFile`, `DiskSpace`.
- `ColimaModel+AppStatus` and `AppStatus`: the status file for the `colimabar` command (what it holds, when the app writes it, when it is stale). `System/AppStatusFile` does the I/O.
- `ReadinessGate`: the wait for "Docker is ready" after a start. The wake of a proxy and the `colimabar` command use it.
- `BusyMarker`: reads the busy marker (label and owner PID) and decides if it is stale.
- `DFGate`: allows one `/system/df` call at a time.
- `LatestOnly`: drops results of overlapping calls that arrive out of order.
- `Models`, `VMState`, `IdleMinutes`: row types, the VM state and the auto-stop times.

### `Docker/`

`DockerAPI` is a small Docker Engine API client over the unix socket. `DockerJSON` holds the JSON wire types.

### `Proxy/`

`SocketProxy` is the auto-start proxy. `SocketProxy+HTTP` parses just enough HTTP to answer pings and to classify requests. `ProfileProxies` owns one `SocketProxy` for each docker profile. `ProfileSocket` derives and checks the path of a profile socket. `UnixSocket` has the socket helpers.

### `Domains/`

Container domains: names such as `web.shop.localhost` for published ports. The pure types decide everything, so tests need no network. `DomainName` makes and checks names and hosts. `DomainPorts` has the proxy ports and the order of container ports. `DomainCandidate` is a running container with its ports and labels (`dev.colimabar.port`, `dev.colimabar.domains`). `DomainRoutes.build` turns the candidates into the table of names and routes, and `resolve(host:)` answers a Host. `HTTPHead` parses the head of an HTTP/1.x request. `DomainPage` writes the error pages. `DomainLink` builds the links. `DomainStatus` is what the System tab shows. `DomainProxy` owns the HTTP listener and the HTTPS listener (each on `127.0.0.1` and `::1`). `DomainSession` handles one client connection: it reads the head, finds the route, connects upstream and splices the bytes. `ColimaModel+Domains` is the glue.

HTTPS: `DER` encodes ASN.1 and `X509Builder` builds certificates (pure). `LocalCA` is the name-constrained certificate authority and signs the leaves. `LocalCAStore` keeps its files (a new set goes in with one rename), and `TrustStore` is the only code that touches the login keychain and the trust settings. `PKCS12` makes a `SecIdentity` of a leaf in memory, and `TLSIdentities` runs the self-test and cleans up the files of older versions. `LeafCache` mints one leaf for each route, with the names of the route and its subdomains. `DomainTLSServer` makes the TLS options of the listener and runs the self-test. `DomainTLSServicing` is the seam for the model tests (`SystemDomainTLS`, `InertDomainTLS`). `ColimaModel+DomainsHTTPS` is the glue.

### `System/`

- `Paths`: all file paths. `colimaDir` and `limaDir` find the Colima folder and Lima's folder with the rule in [Actions and `colima-ctl.sh`](#actions-and-colima-ctlsh). The model checks both folders again on each status refresh and each heartbeat tick.
- `Shell`: runs `colima`, `colima-ctl.sh` and other tools, and opens iTerm or Terminal.
- `HotKey`: registers the dashboard shortcut (see [Keyboard shortcut](#keyboard-shortcut)). `HotKeyBackend` holds the Carbon calls and the saved value, so a test can use fakes. `KeyLayout` gives the key name of the current keyboard layout.
- `Routing`: sets and checks the docker routes. `Routing.useOwnContext()` is the Doctor fix **Use colimabar**.
- `PrivateFileWriter`: writes a file in chunks with the mode 0600 from the first byte. It follows no symlink, and a cancel or an error leaves no file.
- `DiagnosticsProbe`: all the I/O of the diagnostics file (the tools, the log, the log files, the crash reports, the own socket of Colima, the file write). It reads only.
- `IssueLink`: the URL of the bug report form with the fields filled in.
- `DoctorProbe`: all the I/O of Doctor (tool versions, `docker context ls`, the shell files, the docker config file, plugin folders, `colima-ctl.sh stale-files`, `df`). It reads only.
- `NetworkProbe`, `PortProbe`, `HostLookup` and `NetworkObserver`: the I/O of the network checks, see [Network health](#network-health). They read only.
- `DockerConfigFile`: edits the docker config file for a Doctor fix: a private backup `config.json.colimabar-YYYYMMDD-HHMMSS`, then a write through a symlink.
- `AppStatusFile`: writes, reads and removes `app-status.json` (see [Command line](#command-line)).
- `CleanupProbe`: the I/O of the Cleanup page: the log sizes through `colima ssh`, and the `lstat` of the disk image files. It reads only.
- `ProcessProbe`: the start time of a process by PID (`sysctl`), for the busy marker.
- `ProfileContexts`: creates, updates and removes the `colimabar-PROFILE` docker contexts.
- `LoginItem`: the login item.
- `Notifier` and `AlertThrottle`: notifications and their rate limit.
- `ContainerAlertGate`, `RestartLoopTracker`, `QuietWindows`, `ContainerAlertOutcome` and `MutedProjects`: the policy for container alerts, see [Notifications](#notifications). `ColimaModel+ContainerAlerts` feeds the events to the gate.
- `SystemPowerObserver`: reports system sleep and the end of it. It also reports changes of the power state: the charger (`notify_register_dispatch` with `kIOPSNotifyPowerSource`), Low Power Mode and the thermal state. It is the only place that subscribes to power events.
- `PowerState`: on battery, Low Power Mode and a hot Mac, and the heartbeat saving that follows (`PowerState.Saving`). `read()` is the only part that calls IOKit and `ProcessInfo`.
- `Updater`, `Version`, `ReleaseLink`: the daily release check. `Updater+Install` is the in-app install, see [In-app update](#in-app-update). Its parts are `InstallSource`, `ReleaseInfo`, `ReleaseDigest`, `UpdateDownload`, `UpdateVerifier`, `AttestationCheck`, `BundleSwap`, `UpdatePolicy` and `UpdateError`. `UpdateTestHooks` exists only in a test build.
- `Defaults`: `UserDefaults` access.
- `ColimaDirWatcher`: watches the Colima folder, Lima's folder and their subfolders. Lima's folder can be outside the Colima folder (`LIMA_HOME`).
- `FileLimit`: raises the open file limit.

### `Logs/`

The log windows. `LogStore` holds the live state for one container. If the container is gone, it shows the lines that `RemovedLogKeeper` saved. `LogDemuxer` splits the stdout and stderr frames of Docker. `LogLine` is one line with its time, text and stream. `LogTime` parses the Docker timestamps fast, off the main thread. `LogFilter`, `LogBuffer`, `LogTrim` and `LogTail` filter and limit the lines. `LogLimits` holds the limits and timings of a log window. `LogView` and `LogWindows` show the lines. `RemovedLogKeeper` keeps the newest lines of auto-remove containers (`docker run --rm`) while the option is on, and keeps them for 5 minutes after a failure. `RemovedLogRing` is the buffer of one container: the stream thread stores the raw log bytes in it. ColimaBar parses them only when a log window opens.

### `Views/`

The dashboard UI. `Dashboard/` has the frame, header, live tiles, footer and the stopped screen. It also has `ViewState`, the UI state that survives when the popover closes (tab, filter, collapsed groups), and `Sparkline`, the `Shape` that draws the 60-second graphs. `Containers/` and `System/` hold those tabs. `Dashboard/` also has `NewProfileAlert` (the New Profile form) and `DeleteProfileAlert` (the typed confirmation before a profile delete). `System/` also has `CleanupView` (the Cleanup page) and `CleanupRow` (one item row), `VMSettingsSection` (the VM resources and features, on the System tab for a running VM and on the stopped screen for a stopped VM), `SettingsFilePanel` (the export and import panels) and `ShrinkDiskAlert` (the typed confirmation before a disk shrink). `ImagesTab.swift` and `VolumesTab.swift` are the other tabs. `VolumeBackupPanel` has the panels and alerts of volume backup and restore, and `VolumeTransferStrip` the progress strip of the Volumes tab. `Dashboard/` also has `UpdateAlert` (the dialogs of an update) and `LinkAlert` (the question before a link starts, stops or restarts a VM, and the alert for a link text when notifications are off). `Containers/` also has `NetworkNotice` (the notice for a broken port forward or DNS), `InspectView` (the Inspect page of a container), `InspectEnvRow` (one environment or label row), `InspectState` (the detail and the shown values, in `ViewState`) and `ComposeMenu` (the ••• menu of a Compose project). `Doctor/` has `DoctorView` (the Doctor page), `DoctorRow` (one check) and `DiagnosticsPanel` (the save panel of the diagnostics file). `System/` also has `VMConfigView` (the VM settings page), `VMConfigForm` (its state, in `ViewState`) and `VMMountRow`. `System/` also has `ShortcutRecorder` (the row for the dashboard shortcut) and `ShortcutRecording` (the state of the recorder and its event monitor). `Shared/` has the hover hints (`Hint.swift`), all hint text (`Help.swift`), `TypedNameWatcher` (turns on a destructive button when the typed text matches) and small shared views.

## Cross-cutting concerns

### Auto-start proxy

All docker clients use the stable socket (`~/.cache/colima-bar/docker.sock`, `Paths.proxySocket`). Its path never changes, and it follows the selected profile. The user guides call it "the ColimaBar socket". This document calls it "the stable socket". "The proxy sockets" means the stable socket and all profile sockets. `Routing` points each client at the stable socket:

<p align="center">
  <img src="docs/assets/docker-routes.svg" width="900" alt="Each docker client reaches the ColimaBar socket through its own route. While ColimaBar runs, the socket is the proxy. When ColimaBar quits, it is a symlink to the Colima socket.">
</p>

| Client | Route |
|---|---|
| docker CLI and tools that read contexts | The docker context `colimabar`. ColimaBar switches to it from `default` or a `colima*` context at launch, whatever the auto-start setting. While auto-start is on, it also moves a `colima` or `colima-PROFILE` context back at any time. |
| IDEs and Dock apps | `launchctl setenv DOCKER_HOST`. ColimaBar also sets `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` for Ryuk. Both apply to all apps that launchd starts in the session. |
| testcontainers | `docker.host` in `~/.testcontainers.properties`. The write follows a symlink and keeps the file mode. |
| Tools that only try `/var/run/docker.sock` | An optional symlink that needs an admin password (`Routing.linkVarRun()`). |

`Routing.apply(selected:)` runs when the app starts. Colima switches the docker context on `start` and deletes it on `stop`. Thus `ColimaModel.checkDockerContext()` runs `Routing.restoreContext(selected:)`. It runs only while auto-start is on. The triggers are:

- Each VM action that was not cancelled.
- The end of a wake.
- A profile start or stop that `refreshStatus()` sees.
- A change of the mtime of the docker config file (`Routing.configStamp()`, one `stat` for each tick, through a symlink).
- Auto-start turning on.
- A retry 60 seconds after a failed check, at most three times in a row.

When a ColimaBar context is current, the check also sets the launchd and testcontainers routes. It reads `currentContext` from the config file, because `docker context show` fails when the context is missing. `Routing.contextTarget` decides the move. `Routing` never changes a route that points to a different daemon.

The upstream of the stable socket is the Colima socket of the selected profile. While the VM is up, the proxy splices bytes in both directions. While the VM is down, it does this:

<p align="center">
  <img src="docs/assets/auto-start-sequence.svg" width="900" alt="Sequence: the proxy answers a ping itself. A real request calls wakeForProxy, which runs colima start and readiness probes. Then the proxy splices the waiting request on the same connection.">
</p>

- It answers `GET` and `HEAD /_ping` itself, so idle pollers do not start the VM. It needs the daemon API version for this answer. `ColimaModel` stores the version from the last real ping in `UserDefaults`. Until the first one, a ping counts as a real request.
- For the first real request, it calls `wakeForProxy()`. Requests that arrive during a wake wait for the same wake.
- `wakeForProxy()` waits for `colima start` to exit. Then it waits for several successful `/images/json` probes in a row. An open socket does not mean that the Docker daemon is ready.
- After the wake, the request continues on the same connection. If the wake fails, the proxy answers HTTP 503 with a JSON `message`.
- `wakeForProxy()` does not start a deleted non-default profile, or a profile with a runtime other than docker.

On quit, or when auto-start is off, `SocketProxy.stop()` replaces the path with a symlink to the Colima socket. It creates the link before it closes the listener, so a client never sees a missing socket.

The listener is a GCD read source on a non-blocking fd. When a client waits, the event handler accepts all waiting clients and starts one thread for each connection. There is no accept thread for each proxy. Only the cancel handler of the source closes the fd. GCD runs it after the last event handler returns. Thus the system cannot give the same fd number to a new listener while an accept can still run on the old one.

### Profile sockets

`ProfileProxies` runs one more `SocketProxy` for each profile with the docker runtime in the last `colima list`. The socket is `~/.cache/colima-bar/profiles/PROFILE.sock` (`Paths.profileSocket`). Its upstream is the Colima socket of that profile. It changes only when the Colima folder moves (`ProfileProxies.refreshUpstreams()`). A real request to it calls `wakeForProxy(profile:)` for that profile only. The readiness gate and the refusals are the same as for the stable socket.

- `ProfileSocket.path` returns nil for an invalid name, or when the path is longer than 99 bytes: sun_path holds 103 bytes, and `UnixSocket.listen` binds at `PATH.tmp` first. ColimaBar logs the skipped name once.
- `refreshStatus()` calls `syncProfiles()` after each `colima list`. It creates the proxies of new profiles, removes the proxies of gone profiles and deletes old files in the folder. It keeps the proxy of a profile while its busy marker exists, because a disk shrink deletes the profile for a short time. An empty list changes nothing. A debug run changes nothing.
- `ProfileContexts` keeps one docker context `colimabar-PROFILE` for each proxy. It changes only contexts whose description starts with "ColimaBar". It runs the docker CLI only when the wanted set changes. The `colimabar` context, the launchd `DOCKER_HOST` and the testcontainers route still point at the stable socket.
- `wakeForProxy(profile:)` runs one wake at a time for each profile. The stable socket and the profile socket of the selected profile can ask for the same wake.
- `colima start` of any profile switches the docker context to `colima-PROFILE`. `Routing.restoreContext` moves a non-selected profile to `colimabar-PROFILE`, which has the same daemon and auto-start.
- Each proxy holds one listening fd and one GCD read source. It has no accept thread. Thus the idle cost grows by one fd for each profile.

On quit, or when auto-start is off, each profile socket becomes a symlink to the Colima socket of its profile.

### VM state

The heartbeat runs each second while a dashboard is open or an action runs. Otherwise its steps depend on the power state (`PowerState.saving`, `ColimaModel.tickInterval`, `pingInterval` and `staleAfter`). The model uses `.off` while a dashboard is open or an action runs.

| Saving | Tick | Ping | `colima list` (running or stopped) |
|---|---|---|---|
| Dashboard open | 1 s | 3 s | 5 min |
| Action runs, dashboard closed | 1 s | 10 s | 5 min |
| `.off` (charger) | 5 s | 10 s | 5 min |
| `.battery` | 10 s | 20 s | 10 min |
| `.strong` (Low Power Mode, or thermal state serious or critical) | 15 s | 30 s | 15 min |

Each ping time is a whole number of ticks. A VM in another state refreshes after 60 seconds. The proxies and the folder watcher do not depend on the tick. Auto-start and auto-stop read the busy marker directly, so auto-start is not slower. The hourglass for an action from outside the app follows the tick: in Low Power Mode with the dashboard closed, it can lag by up to about 22 seconds.

ColimaBar runs `colima list -j` only in these cases:

- A ping shows that the VM went up or down.
- `ColimaDirWatcher` sees a change in the Colima folder (`Paths.colimaDir`), a profile folder, Lima's folder (`Paths.limaDir`) or a Lima instance folder.
- The dashboard opens and the last list is more than 1 minute old.
- The last list is older than the time in the table above (5, 10 or 15 minutes; 1 minute when the state is not running or stopped).

The model reads the `colima.yaml` of the selected profile after each `colima list` that succeeds, each time the dashboard opens, and after a config edit of a stopped VM.

### Actions and `colima-ctl.sh`

ColimaBar sends the profile in `COLIMABAR_PROFILE`: the selected profile, or the profile of a profile menu action. The script takes a lock for each profile and writes a busy marker while a VM action runs. Its stderr goes to `~/.cache/colima-bar/ctl.log`. Each VM dialog of the script names the profile, for example "Grow the Colima disk of profile 'work' to 150 GB?".

`with_busy` runs the action in an extra subshell, `( "$@" ) &`. Without it, bash 3.2 (the `/bin/bash` of macOS) can run the first `command colima` of the action with `exec`. Then the action ends after that call. For example, `restart_vm` stops the VM but does not start it again. A test with stub tools (`ColimaCtlScriptTests`) checks this.

`profile-create CPU MEM DISK [RUNTIME [VMTYPE MOUNTTYPE]]` runs `colima start` with these values for a new profile. It checks the pair with `recreate_pair_ok` and QEMU with `qemu_ok`. It checks the name with the same rules as `ProfileName.problem`. `profile-delete` refuses the name `colima` and names that start with `colima-`, because Colima reads them as a different profile: it maps `colima` to `default` and removes the `colima-` prefix. It also refuses a profile without a folder. Then it asks once more and runs `colima delete --data --force`. The app shows a typed confirmation before it.

ColimaBar (`Paths.colimaDir`), the script and `uninstall.sh` find the Colima folder with the same rule as Colima. They use the first match:

1. `COLIMA_HOME`, if it is set and the folder exists.
2. `~/.colima`, if it exists.
3. `~/.config/colima`, if it exists.
4. `$XDG_CONFIG_HOME/colima`, if `XDG_CONFIG_HOME` is set.
5. `~/.colima`, the default of Colima.

Lima's folder (`Paths.limaDir`) is `LIMA_HOME` if it is set, else `_lima` in the Colima folder. ColimaBar runs each `colima` command, `colima-ctl.sh` and each Terminal command with `COLIMA_HOME` set to the Colima folder, so Colima uses the same folder. It creates the folder first, because Colima skips a `COLIMA_HOME` that does not exist. Before it creates the folder, the app and `colima-ctl.sh` check the rules again. They create the folder only if the rules still pick it and colima is installed. If the rules now pick a different folder, the script stops the action. A new empty `~/.colima` would otherwise hide `~/.config/colima` from then on. The app reads `COLIMA_HOME`, `LIMA_HOME` and `XDG_CONFIG_HOME` from its launchd environment, not from the shell. The model checks the folders again on each status refresh and each heartbeat tick, so a change needs no restart.

The name checks of the script list each allowed character, not a range such as `[a-z]`. Thus they match only ASCII in every locale.

`vm-config STAGED SHA` replaces `colima.yaml` for the VM settings page, see [VM settings](#vm-settings). `resources`, `rosetta`, `k8s` and `disk` restart a running VM after a dialog. For a stopped VM, they only change `colima.yaml`, and the values apply at the next start (`CtlAction.editsConfigWhenStopped`). They write no busy marker then, so the app shows "Saving" until the script ends. `resources`, `rosetta` and `k8s` show no dialog for a stopped VM. `disk` still asks, because the grow becomes permanent at the next start. If the VM starts or stops while that dialog is open, the script changes nothing and exits with 1. `k8s on` for a stopped VM does not switch the kubectl context. `colima start` switches to it.

`resources CPU MEM` takes a whole number of CPUs and a whole or decimal number of GiB for memory, such as 2.5. Both must be 1 or more. The memory picker of the app shows a value that is not a preset, such as 2.5 GB, as an extra choice. Thus a change of the CPU only sends the same memory again (`ByteFormat.gibText`). A value below 1 GB starts the pick at 1 GB, because the script refuses less. Colima gives Lima the memory in whole MiB, so `ByteFormat.gib(bytes:)` rounds to 2 decimals. While the VM runs, the settings show the value of `colima.yaml` if it differs from the live value by less than 0.006 GiB. The MiB cut and the rounding together stay below that (`VMConfig.shown`).

`run()` sends the VM state that it used for `showsDialog(running:)` in `COLIMABAR_EXPECT_RUNNING` (1 or 0), for each action whose dialog depends on the state (`CtlAction.checksExpectedState`: `resources`, `rosetta` and `k8s`). If the VM is in the other state, for example because it started outside the app, the script changes nothing and exits with 1 (`vm_state`). Thus no dialog opens behind the popover. After a config edit of a stopped VM, `execute` reads `colima.yaml` again before "Saving" ends.

While a `colima start` or `colima restart` for the profile runs (`start_in_progress`), the script refuses `disk`, `disk-shrink`, and `resources`, `rosetta` and `k8s`, before any dialog. It exits with 1. A restart would run a second `colima start` during it, and a shrink would delete the VM while it starts. During a start, `colima status` still fails. Thus while a dialog is open, a start that begins counts as a running VM (`same_state`).

`start_in_progress` uses the same rule as `ColimaModel.isStartInProgress`. The profile is the value of `--profile` or `-p` (also `--profile=NAME` and `-p=NAME`). Else it is the first word after `start` or `restart` that is not a flag and not the value of a flag, such as the `4` of `--cpu 4` (`ColimaModel.startValueFlags`). Else it is `default`. Colima reads `colima` as `default` and removes a `colima-` prefix. `colima start -f` does not count: it is a foreground supervisor. For `colima restart`, `-f` means `--force`, and it counts.

The script reads values of `colima.yaml` in the same forms as `VMConfig.parse`: with CRLF line ends, inline comments and quotes. The script runs `colima status` in a subshell. If the Colima folder changed, the main shell exits after the subshell, without the redirect, so the notice of `cleanup` reaches the app.

A disk cannot shrink in place. `disk-shrink N` saves a copy of `colima.yaml` with `disk: N`, then runs `colima stop`, `colima delete --data --force`, puts the copy back and runs `colima start`. `colima delete` removes the profile folder with `colima.yaml`, so the copy keeps the other VM settings. Colima creates the new disk only at a start. Thus for a stopped VM, the script runs `colima stop` at the end. The busy marker covers the full run. That start switches the docker context, so the model checks the context after the shrink like after any VM action. While the busy marker exists, the model does not switch away from a profile that `colima list` no longer shows, and auto-start waits.

The script puts its PID in the lock (`lock.PROFILE/pid`, written through a temporary file and `mv`) and in line 2 of the busy marker (line 1 is the label). A leftover is stale when `ps` shows that its owner is gone, or that the PID belongs to a process that started after the file was written (`owner_check`, with `ps -o command=` and `ps -o etime=`). If the PID cannot be read, the lock follows the 30-minute rule. A lock folder with no PID file, left by an owner that is ending, is removed, not given back. Age alone does not free a lock whose owner runs, so a long sleep of the Mac cannot free the lock of an action that still runs. A lock or marker with no PID (older versions) keeps the old rule: 30 and 20 minutes. `ColimaModel` reads the marker with `BusyMarker` and `ProcessProbe` and removes a stale one.

`vm-recreate VMTYPE MOUNTTYPE` changes `vmType` and `mountType`, which Colima fixes when it creates the VM. It checks the pair (`recreate_pair_ok`, the same list as `VMTypeRules`: a test compares them), refuses the names `colima` and `colima-*`, an `x86_64` VM with vz, qemu without QEMU, and qemu with `network.address` or `network.mode: bridged`. After the lock, the start check and the dialog, it copies `colima.yaml` to `colima.PROFILE.yaml.before-recreate` and `.recreate` in `~/.cache/colima-bar`, sets the keys in the second copy and runs `colima stop`, `colima delete --force` (never `--data`: Colima then keeps its Docker data disk and mounts it in the new VM) and `colima start` with the copy in place of `colima.yaml`. It runs `trap '' PIPE`, so a quit of ColimaBar does not end it between the delete and the start. If the script ends with no `colima.yaml` (a signal or the time limit), `cleanup` puts the `.recreate` copy back. `CtlAction.timeout` is 1800 s for this action and 900 s for the others.

`stale-files` prints the pid files of Lima and of the Colima daemon that they cannot use, as `reason<TAB>path<TAB>pid` lines (`gone`, `reused`, `invalid`). It takes no lock, writes no busy marker and runs no `colima` command. `repair` is the action behind Doctor's **Repair**: see [Doctor](#doctor).

`compose-pull`, `compose-up` and `compose-down` take `NAME DIR NENV ENV... FILE...` (`ComposeProject.ctlArgs()`; `NENV` is the number of env files, 0 to 16). They run `docker compose -p NAME --project-directory DIR [--env-file E]… -f F1 -f F2 … pull|up -d|down` against the profile socket (`DOCKER_HOST` of the script). They are not VM actions: no lock and no busy marker. The script checks the name (a list of characters, not a range), the folder and the files again, and checks `docker compose version` first. Only `compose-down` asks (`confirm`), and a plain `down` keeps the volumes and the images. The script runs docker in the background and saves its output, with stderr, in a private file under `~/.cache/colima-bar`. It prints the file to stdout and removes it on every exit, so a stop on the time limit also stops docker, and the output never reaches `ctl.log`. A failure notification has no output text. A space before each line that looks like a `COLIMABAR_NOTIFY:` notice stops the output from posting a notification. `ColimaModel.compose(_:project:)` runs the script through `Shell.run`, posts the notices, and keeps the last 200 lines of output for each project in memory only (`composeOutput`, keyed `profile/name`, for **Copy Last Output**), says so when the time limit of 15 minutes stopped the run, and checks the files of the projects off the main thread after each container refresh (`composeMissing`). A debug run does nothing.

`ctr-debug ID IMAGE` opens a shell in a new container (`docker run --rm -it --name colimabar-debug-<12 hex> --pid container:ID --network container:ID --cap-add SYS_PTRACE IMAGE`) against the profile socket, so it never starts a stopped VM. It is not a VM action. ID must be 64 hex characters, never a name, and IMAGE must pass `DebugShell.isValidImage`. The script checks both again with written-out character lists. If the new container already runs, the script opens a second shell in it with `docker exec`. `ctr-shell` first runs `docker exec NAME sh -c :`. If the error says `executable file not found`, it prints a hint that points to Debug shell. The image comes from the hidden key `debugShellImage` (`Defaults`), which is not in the settings file.

`log-truncate ID [NAME]` empties the json log file of a container in the VM. The script checks that `ID` has 64 lowercase hex characters and builds the path itself, so no path comes from the app. It runs `sudo -n truncate -c -s 0` (`-c` creates no file) and asks first. A name with a character outside the list shows the short ID in the dialog. `disk-trim` takes the lock, writes the busy marker "Trimming disk" and runs `fstrim -av` in the VM (exit 64, a partial failure, is a success if a line says "trimmed"). It never starts the VM. Its stdout goes to the app, which reads the trimmed bytes from it. `auto-prune` is the weekly cleanup: no dialog, a quiet lock (`lock_vm quiet`), and exit 2 for a stopped VM, a start in progress or a held lock, so it never starts the VM. It shares `prune_dangling` with `prune dangling`. `prune cache` removes the unused build cache. The `ssh` calls use `command colima ssh --profile "$PROFILE" --`, not the `colima` function: the function puts `--profile` after the arguments, and they would go to the remote command.

The exit codes are fixed. 0 means done. 1 means failed, and the script already notified the user. 2 means cancelled, or another VM action holds the lock. ColimaBar shows nothing for 2.

### VM settings

The advanced VM settings change keys of `colima.yaml` that `resources`, `rosetta`, `k8s` and `disk` do not cover: `network.dns`, `network.address`, `portForwarder`, `mountInotify`, `mounts`, `docker.registry-mirrors` and `docker.insecure-registries`. Only `colima-ctl.sh` writes `colima.yaml`, and it owns the lock, the dialog and the restart. But bash 3.2 and `sed` cannot edit a list safely. Thus Swift makes the new text, and the script puts it in place:

1. The form (`VMConfigForm`) holds the edits. `change` is a `VMSettingsChange` with only the fields that differ from `colima.yaml`. `VMSettingsCheck` gives the problems, and **Apply** stays off while there is one.
2. `ColimaModel.applyVMSettings(_:profile:baselineSHA:)` is async and returns a `VMApplyOutcome`. It returns `skipped` in a debug run or while the profile is busy (`mayApplyVMSettings`). It reads `colima.yaml`, takes its SHA-256 (CryptoKit) and compares it with the SHA of the file that the form shows (`VMConfigForm.baselineSHA`, from `ColimaModel.vmSettingsSHA`). If they differ, it stops with `changedOutside`, notifies and reads the file again. Else it checks the change again and builds the new text with `ColimaYAML.apply`. If the file has the values already, it returns `alreadyThere`. After `applied`, `alreadyThere` or `changedOutside`, the page loads the form again from the file (`VMConfigForm.shouldReload` does the same when the file changes while the form has edits that equal the file).
3. It writes the new text to `~/.cache/colima-bar/colima.PROFILE.yaml.new` (created with `O_CREAT|O_EXCL|O_NOFOLLOW` and mode 0600, in the 0700 state folder; an old file or link there is removed first; a failure gives the path and the errno text) and runs `colima-ctl.sh vm-config STAGED SHA`. After a good run, it drops the Doctor report, because the VM settings changed.
4. It accepts only a regular file, not a link, at exactly this path. It takes the lock and reads the VM state (`COLIMABAR_EXPECT_RUNNING` applies). If the SHA-256 of `colima.yaml` is not `SHA`, it changes nothing and exits with 1: the file changed outside ColimaBar.
5. Running VM: the upgrade dialog, then one dialog, then a second SHA and state check (the dialog can stay open). It copies `colima.yaml` to `colima.PROFILE.yaml.bak`, puts the staged file in place (a copy in the same folder, then `mv`) and restarts the VM. From the moment the new file is in place, `INSTALLED` is set. If the restart fails, or the script ends before the restart ends (a TERM or the 900 s limit of ColimaBar), `cleanup` puts the backup back and tells the user. It does not start the VM again. If the `colima stop` failed (`STOP_FAILED`), the VM still runs, and the message says that nothing changed. Stopped VM: it makes the backup and puts the file in place. It never starts the VM. Every exit removes the staged file.

`ColimaYAML` works on lines. It finds the span of a key: the key line, and the indented lines or `- ` items below it. It replaces only that span. A missing key goes after the last line of its section. A missing section goes at the end of the file. `docker: {}` becomes a block that keeps its other keys. All other bytes stay: comments, unknown keys and their order. A file with CRLF keeps it. A field that already has the new value is not written, so its comments stay. It reads a plain value, `null`, `~`, `[]`, `{}`, a flow list on one line and a block list. A tab after the colon counts. A quoted key (`"dns":`) makes the field read-only, so the editor never adds a second key. `mounts` has three states: no key or `null` (Colima 0.10.3 mounts nothing), `[]` (it mounts the home folder, writable, `VMSettings.Read.mountsDefaultHome`) and a list. An anchor, a tag, a block scalar, a list over several lines, or a mount with a key other than `location`, `writable` and `mountPoint` makes the field read-only (`ColimaYAML.Failure`). It writes lists in the flow form, and mounts in the block form.

Colima rewrites `colima.yaml` at each start (`--save-config`), so it drops comments and unknown keys anyway. ColimaBar still keeps them, because the user can read the file. Colima ignores a change of `vmType`, `mountType`, `arch`, `runtime` and `network.mode` after it created the VM. Thus the page shows `arch` and `runtime` as read-only, and changes the VM type and the mount type only through a recreate, see [VM type change](#vm-type-change). Once `network.address` is on, Colima does not turn it off. `VMInfo.ipAddress` comes from `colima status -j` (`ip_address`).

### Doctor

Doctor checks the setup of the selected profile. It runs only on request: the **Run checks** button, or the Doctor page when it opens and the last report is more than 5 minutes old (`DoctorReport.staleAfter`). It never runs from the heartbeat. The checks never send a notification. **Use colimabar**, **Set routes**, **Use osxkeychain** and **Add folder** send one with the result. **Repair…**, **Restart**, **Use ssh forwarder** and **Use the Mac's DNS** send one only if they fail. **Copy line** sends none. One run at a time (`isDoctorRunning`). A profile switch drops the result of a run in progress (`generation`). A request during a run (`isDoctorRunQueued`) makes the run start once more, so the new profile gets its report. A probe that fails gives a skipped or warning result, never an OK: a failed `colima list` (`refreshStatus()` returns false), a failed `stale-files`, a failed `df`, a tool that does not run, a file that cannot be read.

- **Design.** `DoctorProbe` reads the system (the only I/O), `ColimaModel.collectDoctor()` fills `DoctorInputs`, and `DoctorRules.evaluate` gives one `DoctorResult` for each `DoctorCheck`. The independent probes run in parallel (`async let`) and each has a time-out of 5 to 15 seconds. No probe starts the VM: it uses `docker --version` (not `docker version`), `docker context ls` and, only while the VM runs, `colima ssh -- df -Pk`, the two network checks (see [Network health](#network-health)).
- **Context and routes** reuse the code of the docker context check: the current context comes from `Routing.currentContext()` (the config file), the list from `Routing.existingContexts`, the routes from `Routing.status()`. The fixes call `Routing.useOwnContext()` and `Routing.apply`.
- **Shell.** `ShellStartupScan` reads the text of the startup files of the login shell. It runs no user code, so a new terminal can still differ.
- **Registry login.** `DockerConfig` reads helper names only. It never reads `auths`.
- **Fixes.** **Use colimabar**, **Set routes**, **Copy line** (`CtlAction.copyEnv`), **Use osxkeychain**, **Add folder**, **Repair…**, **Restart** (`restartVM`), **Use ssh forwarder** (`useSSHForwarder`) and **Use the Mac's DNS** (`useMacDNS`). The last two call `applyVMSettings`. Each fix except **Copy line** runs the checks again. The two docker config fixes go through `DockerConfigFile.edit`.
- **Repair.** `colima-ctl.sh repair` takes the lock, refuses without a `colima.yaml` and while a start runs, and asks first. Then it runs under the busy marker "Repairing": (1) remove the pid files whose PID was reused or is not a number, before the force stop, so Lima never sends SIGKILL, and Colima never sends SIGTERM, to that process. If a file stays, notify and stop before the force stop; (2) `colima stop --force`, whose failure is logged; (3) if a Lima process of the VM still runs, fail and remove nothing more; (4) remove the other stale pid files; (5) `colima start`. The script decides and deletes in one process, under the lock. Only regular files (never links) are removed: `ha.pid`, `vz.pid`, `qemu.pid` and `krunkit.pid` of the instance of the profile, and `usernet_NAME.pid` of a network when no instance has a live host agent, and `PROFILE/daemon/daemon.pid` of the Colima folder (the owner must be `colima daemon`; `colima stop` and `colima start` run `pkill -F` on this file with no owner check). It never touches disks, `cidata.iso`, `*.yaml`, logs or sockets. `CtlAction.repair` is a VM action, so the model checks the docker context after it like after any VM action.
- **UI.** `ViewState.showDoctor` makes `DashboardView` show `DoctorView` between the header and the hint bar. The page scrolls inside the fixed popover size. Entry points: the System tab, the stopped screen (only when `colima list` shows the profile Broken or its last start failed, `ColimaModel.doctorHint`) and the right-click menu.
- **Debug runs.** A debug run may run the checks (they only read). It makes no fix and no repair: the buttons are disabled and `applyFix` and `repairProfile` check `isDebug`. `COLIMABAR_DOCTOR=1` with `--snapshot` opens the Doctor page.
- **Upgrade row.** `DoctorRules.upgrade` compares `DoctorInputs.lastGoodVersions` with the versions of `tools`. It has no fix, see [Upgrade guard](#upgrade-guard).
- **Diagnostics.** `DoctorReport.text(home:version:)` is the Doctor part of the diagnostics file. See [Diagnostics](#diagnostics).

### Network health

Two checks find what a restart fixes: a published port that answers in the VM but not on the Mac, and a VM that cannot resolve host names while the Mac can. Both run only while the VM already runs. They use the Colima socket of the profile and `colima ssh --profile P`, never a proxy socket or the `colimabar` docker context, so they never start a VM. They never poll. `ColimaModel+NetworkHealth` holds the triggers, `NetworkProbe` the I/O.

- **Ports.** `PortHealth.targets` takes the TCP ports of the running containers from `GET /containers/json` (`Type`, `IP`, `PublicPort`): the addresses `0.0.0.0`, `::`, `127.0.0.1` and `::1`, no UDP, no duplicates, at most 32. Other addresses are only counted. With Kubernetes and `network.address`, Colima ignores the ports 80 and 443, so they are left out. `PortProbe` connects to `127.0.0.1` without blocking (1 second), waits 0.5 second and peeks at the socket (`MSG_PEEK`). Data or silence is open. A close at once is closed (a dead forward accepts and closes). It sends no data. It runs 8 ports at a time on dispatch threads. Only ports that are not open on the Mac go to the VM, in one `colima ssh -- bash -c SCRIPT` call (15 seconds). `PortHealth.vmScript` builds the script from integers in 1...65535, so no container text reaches a shell. The script starts each probe in the background and ends with `wait`, so many quiet ports do not add up to the time limit. A local failure of a socket call is `error` and counts as unknown, never as broken. A port is broken if the VM answers and the Mac does not. A port that answers nowhere is not an alarm. A broken port is probed again on the Mac after 5 seconds (`PortHealth.confirmed`).
- **DNS.** `NetworkObserver` watches `State:/Network/Global/DNS`, `State:/Network/Global/IPv4` and the pattern `State:/Network/Service/.*/DNS` with `SCDynamicStore` on the main run loop. It needs no permission. It uses no `NWPathMonitor`. `MacDNSConfig.parse` is pure. It makes the servers, the split domains (supplemental match domains) and a fingerprint. The observer reports only a new fingerprint, and it holds no address or name in clear text. A report starts a 10-second wait, and a newer change restarts it. Then each running profile with no busy marker, action or auto-start runs `colima ssh -- bash -c 'timeout 5 getent ahostsv4 registry-1.docker.io; echo "colimabar-status=$?"'` and, at the same time, the Mac look-up `HostLookup` (`getaddrinfo` on its own thread, 5 seconds, `Deadline`). `colima ssh` exits with 1 for every failure of the remote command, so the exit status of `getent` comes from the marker line, and a missing marker or a failed `colima ssh` is unknown. `DNSHealth.verdict` is `ok` if the VM resolves, `macOffline` if neither resolves (no alarm), and `broken` if only the VM fails. A broken result is checked again after 20 seconds. An unknown or `macOffline` result, and a failed `colima ssh` in the ports check, keep the earlier report and the throttle. A sleep cancels the checks and pauses the network trigger until the after-wake path ran. One notification for each profile and kind every 60 minutes (`ColimaModel.networkAlertAllowed`). With an empty `network.dns`, the Lima host agent answers for the VM through the Mac, so a restart gives it the new setup. With servers in `network.dns`, the fix is **Use the Mac's DNS**, which clears them (`VMSettingsChange(dnsServers: [])`). It never copies the Mac servers.
- **Triggers.** After a sleep, `checkAfterSleep` waits 15 seconds after the ping and the clock check, then checks the ports of the profile (it can notify). When the dashboard opens, `becameVisible` checks the ports of the selected profile if the last check is more than 5 minutes old (no notification). A DNS change checks the DNS. **Check again** and Doctor check both. A check stops quietly if the task is cancelled, an action or a start began, or the VM stopped.
- **State.** `portHealth` and `dnsHealth` hold the last report of each running profile. A property changes only when the report changes (`set`). `forgetNetworkHealth` and `pruneNetworkHealth` drop reports of a profile that restarted or stopped. `NetworkNotice` shows a notice for the selected profile.
- **Notifications.** Only a confirmed broken result notifies, with the **Restart** button. An own `AlertThrottle` of 60 minutes, keyed `ports|P` and `dns|P|FINGERPRINT`, stops repeats. A good result resets the key. The texts hold no address or domain. A debug run never notifies.
- **Doctor.** `portForwarding` and `vmDNS` come after `diskSpace`. `DoctorInputs` has `ports`, `portForwarder`, `dns`, `dnsOverride` and `macSplitDomains`. A split-DNS warning needs servers in `network.dns` and a split domain on the Mac. `DoctorResult.shareDetail` hides the domains.
- **Debug runs and the command.** No `NetworkObserver`, no wake check, no check when the dashboard opens, and no notification. Doctor, also in `colimabar doctor`, runs both checks: a TCP connect with no data, `colima ssh`, `getaddrinfo` and a read of the Colima socket. They only read, and they need a running VM, else they are skipped. The Mac DNS setup is read through `NetworkObserver.readCurrent()`. The `doctor` JSON gets the new check ids. `schemaVersion` stays 1.

### Diagnostics

**Save Diagnostics…** and **Report an Issue…** (the Doctor page, and the right-click menu for the second) write one plain text file, `ColimaBar-diagnostics-YYYYMMDD-HHMMSS.txt`. The user chooses the place in an `NSSavePanel`, which gives access without a Desktop permission prompt. The file has the mode 0600 and at most 2 MB. It is text, not an archive, so the user can read it.

- **Parts.** `DiagnosticsPart` lists them in file order, each with a time-out and a cap. `DiagnosticsProbe` reads them. `ColimaModel.collectDiagnostics()` runs all at once, each in `Deadline.run`, so a part that does not answer fails alone with its reason. `Deadline` uses unstructured tasks, because a task group would wait for `Shell.run`, which ignores a cancel. The winner of the race cancels the timer task. A late process ends at its own `Shell.run` time-out. A part can end as ok, skipped, failed or partial (a reason says what is missing). Every part ends before the 20 s cap. `colima status` and the engine part run only while the VM runs.
- **No start.** The parts use no proxy socket. The engine request goes to the own socket of Colima (`Paths.socket`), only while the VM runs. The tools used do not call the daemon: `docker --version` and `docker context ls`.
- **Doctor.** A fresh report is reused. Else the file runs Doctor next to the other parts, or waits for a run in progress.
- **Redaction.** `DiagnosticsBundle.render` runs `Redactor` once over the final text, so no part can skip it, and it runs off the main actor. `IssueLink` redacts first, then cuts each line. The rules include the names in docker request lines (`RequestPath`: the proxy log hides them too) and the host names of registries (`DoctorResult.shareDetail`). `Redactor` is pure: it gets the home folder, the user names and the names of the Mac as input (`DiagnosticsProbe.redactor()`). The rules are in its doc comment.
- **Limits of the data.** `colima.yaml` shows the values of a fixed list of simple keys (`ColimaConfigSummary`). A crash report keeps a fixed list of keys (`CrashReportDigest`). There is no container name, image, volume, variable or `/info`.
- **Issue link.** `IssueLink` fills the fields `macos`, `colimabar`, `colima`, `runtime` and `diagnostics` of `bug_report.yml`. It uses RFC 3986 unreserved characters only and has at most 4,000 bytes. It drops lines from the end of `diagnostics` first and never cuts the versions.
- **One at a time.** `isSavingDiagnostics` guards the run. The buttons and the menu item are disabled meanwhile. A write failure sends a notification with the reason. A debug run prints it on stderr and exits with 1.
- **Debug runs.** A debug run may save the file. `--diagnostics PATH` does it without a panel, opens nothing and quits.

### Inspect, Compose and debug shell

- **Debug shell.** A debug shell is built only from a checked hex ID and a checked image name. Each word goes into the terminal command only as a word quoted with `Shell.quote`, and the script checks both again.
- **Inspect.** The Inspect page reads the environment, the labels and the command of a container. Their values never go to `Logger`, `Notifier`, the diagnostics or the status file. The page holds them in `InspectState` only, and `ViewState` clears it when the page closes. `EnvMask` hides a value by its key or by its shape. It uses `Redactor.isSecretKey` and `Redactor.hasSecretShape`, so the page and this file use the same rules. `EnvMask.maskArgs` also hides the values of flags that hold `pass`, `auth`, `secret`, `token` or `key`, and secret values inside one word (for example `sh -c`). The compose output is in memory only, and the script does not write it to `ctl.log`. `inspect(id:)` gives `.unavailable` when the VM does not answer and `.failed(reason)` for an HTTP status or a decoding error. The reason has no values, and the page logs it once for each open.

### Volume backup

**Back Up…**, **Restore from Backup…**, **Restore to New Volume…** and **Back Up All…** in the Volumes tab save the files of a volume to a tar archive and copy them back. The user chooses the file or the folder in a panel.

- **Socket.** `VolumeBackupRunner` gets the `DockerAPI` of the selected profile, so it uses the own socket of Colima and never starts the VM. It needs a running VM. `ColimaModel.canTransferVolumes` is false in a debug run, while the VM is down and while another transfer runs. One transfer at a time (`volumeTransfer`). A VM stop or a profile change cancels it (`clearVMData`). Shrink and Delete Profile refuse while a transfer runs.
- **Helper image.** `HelperImage.archive(arch:)` builds a `docker save` archive of about 3 KB on the Mac: `manifest.json`, `config.json` and a layer with one empty folder `/v`. The `diff_ids` entry is the SHA-256 of the layer, and the bytes depend only on the architecture (`GET /info`, `aarch64` to `arm64`). `POST /images/load?quiet=1` loads it as `colimabar-helper:1`. Thus nothing is pulled, and it works offline. The runner skips the load if the image exists, and deletes the image at the end (a 409 is no error).
- **Helper container.** It is created and never started: the archive calls of the API work on a created container. It has `NetworkDisabled`, the command `/none`, the volume mounted at `/v` (read-only for a backup) and both labels `com.imohitkr.colimabar.helper=1` and `com.imohitkr.colimabar.helper.kind=volume`. After each operation, the runner deletes it with `force=1` and never with `v=1`, so the volume stays. The Containers tab and the crash alerts leave out containers with the helper label (`ColimaModel.visibleContainers`, `isInternalContainer`). On the first good container refresh of each profile in a normal run, `sweepLeftovers` deletes the containers with both labels and the image. It asks before each delete if a transfer runs, and then stops. If Docker cannot delete a helper container, or the VM stops during a transfer, the sweep of that profile runs again after the next refresh. A debug run does none of this. The debug shell sidecar does not use these labels.
- **Backup.** `GET /containers/ID/archive?path=/v` streams through `StreamHandle`. The reader thread feeds each chunk to `TarScanner` and then to `PrivateFileWriter`. The bytes go to `NAME.PID.tmp`. After the end marker arrived and `fsync` ran, `PrivateFileWriter.commit` renames the file to its name: over the old file after a confirmed replace, else with `renamex_np` and `RENAME_EXCL`, so Back Up All never replaces a file. Two volumes with the same file name get `-2` (`VolumeBackupName.fileNames`). Back Up All stops at the first full disk, and its notification gives the reason of each failed volume. The first entry is `.colimabar-volume.json` (at most 64 KB: the name, the driver, the labels, the creation time and the app). The Docker stream follows unchanged. An error, a cancel or a cut stream removes the file.
- **Restore.** `TarFileScan` reads the whole file before anything changes. It reads the first entry (`VolumeBackupMeta.readHead`), then checks every header and seeks over the data. `TarScanner` refuses an absolute path, a `..` part, a name that is not `v` or below `v/`, a hard link to a target outside `v/`, a device and a file that ends early. It reads ustar, PAX (`path`, `linkpath`, `size`) and GNU long names. A symlink target is not checked, because Docker extracts in a chroot. `VolumeRestoreFlow` then follows `VolumeRestorePlan`: a new name creates the volume (labels only if the name is the same as the old name), an empty volume is used as it is, a volume with files needs a confirmed replace (delete, create again with its own labels), and a volume that containers use is refused. A volume with a driver other than `local`, or with options (a bind folder or NFS), is never replaced. A create answers success for a volume that exists, so after a create for a new name the flow checks again that the volume has no user and no file, and it never deletes a volume that it cannot prove it made. `PUT /containers/ID/archive?path=/` sends the file from the end of the first entry, with `Content-Length`, in chunks of 64 KB (`DockerAPI.upload`). A failed or stopped restore removes a volume that the run created. After a replace deleted the old files, a failure says so and names the file to restore again. The notification of a stop says what changed: nothing, the new volume is gone, or the volume can hold part of the files.
- **Cancel.** `VolumeBackupRunner.cancel()` shuts the socket down. The operation ends, the runner deletes the helper container, and the writer removes the file. A VM stop or a profile change cancels the same way, and the notification says why (`VolumeTransferStop`).
- **Texts.** Notifications name the file, never the path. Docker messages are cut to 120 characters.

### Cleanup

The Cleanup page (`CleanupView`) replaces the tabs, like Doctor and the VM settings page. **Clean Up…** in the Disk usage section of the System tab opens it (`ViewState.showCleanup`).

- **Data.** The page makes no new Docker request. `refreshDF()` decodes `GET /system/df` and calls `applyDF(_:)`. It sets `df`, `images` and `volumes` as before and builds a `CleanupReport` (`CleanupReport.make(from:)`) from the same decode. `wantsDF` is also true while the page is on screen, so `DFGate` still limits the calls. The report holds at most 10 rows in each section (5 for the build cache), the largest first, with the equal sizes in a stable order.
- **Logs.** `refreshLogSizes()` runs `colima ssh --profile P -- sudo -n sh -c SCRIPT`. The script is the constant `LogFileSizes.vmScript`: no container text reaches a shell. It prints `size path` lines and the marker `colimabar-status=0`. `colima ssh` exits with 1 for every failure, so the marker decides. A line counts only if its path is exactly `/var/lib/docker/containers/ID/ID-json.log` with the same ID twice, and the parser reads at most 2048 lines. The call runs only while the page shows, one at a time and at most once in 60 s. A container that the df list does not know is left out, and so is a helper container. A cancelled check (Done, a profile switch) sets no error and no check time. A failed check shows the last line of the error output. The page starts the check again when the VM state changes. `CleanupReport` lists a volume only with usage data and no references, and a container only in the state exited, created or dead.
- **Disk image.** `DiskImageSize` measures `INSTANCE/disk`, `INSTANCE/diffdisk` and `_disks/INSTANCE/datadisk` in Lima's folder with `lstat`. Lima keeps the files sparse, so the allocated size (`st_blocks * 512`) is the real use. A symlink and a file that is not regular do not count.
- **Return Free Space.** `trimDisk()` measures the disk image, runs `disk-trim`, waits `DiskTrim.settleDelay` (the Mac side can lag), measures again and posts `DiskTrim.message` with the sizes before and after. `trim_disk` prints the `fstrim` output, and `DiskTrim.trimmedBytes` reads both output formats of util-linux. The model sets `isTrimming`, and the button is off while it is set or an action of the profile runs.
- **Weekly cleanup.** The setting `scheduledPrune` is off by default. `checkScheduledPrune()` runs in `tick()` after `checkOtherProfilesIdle()`. `PruneSchedule.mayRun` needs: the setting on, no debug run, no update restart, a running docker VM, no busy marker, no action in flight, no wake, no volume transfer, no Return Free Space run and no proxy transfer. The proxy transfers are the live docker traffic that auto-stop also uses: a build or a pull shows no running container, and a prune can delete the image that it is about to use. `PruneSchedule.isDue` needs seven days since the last run and no wait. The model keeps the wait in `pruneRetryAt`. A claim of the run sets it to one hour. When the run ends, `PruneSchedule.retryAt` sets it: none after exit 0, 6 hours after exit 1 (a failure notifies at most four times a day) and one hour after exit 2 (the VM is down or busy). Only exit 0 counts as a run. The setting off clears the waits. `auto-prune` runs `prune_dangling` under `with_busy "Cleaning up"`, so the busy marker shows and TERM reaches docker. The last run of each profile is in `Defaults.Key.scheduledPruneLastRun`. It is machine state and not in the settings file.
- **Debug runs.** A debug run trims no disk, empties no log and runs no weekly cleanup. It may read the log sizes and measure the disk image. `loadCleanupFixture` shows a fixture file (`COLIMABAR_CLEANUP_FIXTURE`) and works only in a debug run.

### Upgrade guard

A new minor or major version of Colima or Lima can change the VM disk. ColimaBar asks before the first start after such a change.

- **Record.** `Defaults.Key.goodStartVersions` holds a JSON string (`GoodStarts`): for each profile, `colima`, `lima` and `macOS` at the last good start. It is machine state, so `SettingsTransfer` leaves it out, and `uninstall.sh` removes it with the other defaults. `DoctorProbe.versions()` reads Colima and Lima in parallel (5 s each) and adds macOS. A tool that gives no version goes in the log once for each launch and tool. `GoodStarts.decodeChecked` decodes each entry on its own, so one bad entry does not drop the others, and it logs the problem without the content. A record needs a known version of Colima and Lima (`UpgradeGuard.canSave`). A debug run never writes or prunes it (`saveGoodStart` checks `isDebug`).
- **Good start.** `execute()` saves after exit 0 for an action where `CtlAction.startsVM(running:)` is true, and only if the script printed the line `COLIMABAR_STARTED` (`start_vm` in the script, after a good `colima start`). Thus a disk change of a VM that stopped outside ColimaBar saves nothing. A warning action reads the versions before the script runs. Another start action reads them next to the script. `performWake` saves only when it ran `colima-ctl.sh start` itself, the script exited 0 with the marker and the readiness gate passed. A start outside ColimaBar, exit 1 or 2, a time-out and a failed gate save nothing. A running profile with no record gets one from `refreshStatus` once for each launch (`upgradeSeedTried`, set only after a probe that gave both versions). A seed never replaces a record (`GoodStarts.seeded`). `syncProfiles` prunes the records of profiles that `colima list` no longer shows. It skips an empty list and keeps a profile with a busy marker.
- **Risk.** `ToolVersions.changed(from:)` gives `VersionChange` values (patch, minor, major, downgrade, from `Version.parts`). `UpgradeGuard.riskyChanges` keeps a minor or major bump or a downgrade of Colima or Lima. A side that is nil or "unknown" gives no change. `riskyChanges` is empty unless the record and the current versions of Colima and Lima are known. Thus nothing blocks a start when a version cannot be read, and the auto-start notice does not repeat when a save is refused. `UpgradeGuard.warning` holds the decision for a manual start.
- **Manual start.** For an action with `CtlAction.warnsAfterUpgrade(running:)`, `execute()` reads the versions. If the change is risky, it calls `dismissPopover()` and gives `COLIMABAR_UPGRADE_NOTE` and `COLIMABAR_RELEASE_NOTES` to the script (`CtlAction.environment(upgrade:)`). The script function `upgrade_confirm` runs after `lock_vm` (inside the `VM_UP=1` branch for config actions, before their own dialog). Cancel, **Release Notes** and no answer exit with 2. An AppleScript error other than -128 writes the error to `ctl.log`, notifies and exits with 1. **Release Notes** opens a URL only if the whole URL matches `https://github.com/(abiosoft/colima|lima-vm/lima)/releases/tag/vN(.N)*`. `UpgradeGuard.releaseNotes` builds the URLs from the digits of the version.
- **Auto-start.** It never blocks and passes no note. After a good wake, `recordGoodWake` sends one notification if the change is risky. A click opens the first release page. Then it saves the record, so each risky change notifies once.
- **Doctor.** The `upgrade` check shows the change. See [Doctor](#doctor).

### Auto-stop

`AutoStopRule.evaluate` holds the idle rule for one profile. A profile is idle when no container runs, no `colima-ctl.sh` action that ColimaBar started runs (`blocksAutoStop`) and its proxies have no active transfers. A transfer is a connection whose latest request is a build, pull, push, load, save, commit or BuildKit session (`SocketProxy.isWork`). Each profile has its own idle time. The timeout setting is the same for all.

- `checkIdle()` checks the selected profile at each tick. It counts the transfers of the stable socket and of the profile socket of the selected profile. Before it stops the VM, it gets a fresh container list. If that fails, it does not stop. While that check runs, `checkIdle()` does nothing. After the list, it reads the limit again and stops only if the idle time (`AutoStopRule.stillDue`) is still over.
- `checkOtherProfilesIdle()` checks each other running docker profile (`AutoStopRule.otherProfiles`). A transfer or a busy marker resets its idle time at each tick. Each 30 seconds (`AutoStopRule.otherCheckInterval`), it gets a fresh container list from the socket of the profile. A failed list does not count as idle. When the idle time is over, it runs `auto-stop` for that profile.
- The idle time uses `SuspendingClock`, which stops while the Mac sleeps, as the VM does. Thus the sleep time never counts, and a dark wake needs no event. The idle time does not restart after a sleep: on a laptop that sleeps often, it would never stop the VM. `idleSince` is the wall time for display. `autoStopAt` is the stop time (`AutoStopRule.stopTime`). It moves later by the sleep time.
- `AutoStopRule.limit` gives the idle time for the power state: at most 10 minutes on battery and at most 5 minutes in Low Power Mode, while `autoStopSooner` is on. A shorter user time stays. The thermal state does not change it. `checkIdle()` and `checkOtherProfilesIdle()` read the limit at each check. A power change keeps the idle start, so the stop time moves at once. A change of the `autoStopSooner` setting restarts the idle time, as a change of the minutes does.
- `checkIdle()` and `checkOtherProfilesIdle()` do nothing in a debug run.

### System sleep

The word for the Mac sleeping is "system sleep". The word "wake" means auto-start in this code (`wakeForProxy`). Only `NSWorkspace.didWakeNotification` uses it for the Mac.

`SystemPowerObserver` calls `systemSleepBegan()`, `systemSleepEnded()` and `powerChanged(_:)` of the model. The model creates it in a normal run only.

- `systemSleepBegan()` and `systemSleepEnded()` cancel the check that runs. The newest check wins.
- `recoverAfterSleep()` opens the `/events` stream again (it can hang after a sleep without an error), opens the stat streams again if a dashboard is on screen, and runs `refreshAll()`.
- `checkAfterSleep(_:)` runs for each profile in `AfterSleepCheck.profiles`: running, docker runtime, valid name, no busy marker, no action in flight and no auto-start. The profiles run in parallel. It waits 0, 1, 2, 4 and 8 seconds before each ping. Each ping has a 3-second time-out, so the check ends within about 30 seconds. Before each try and each notification, it stops quietly if the task is cancelled, an action or a start began, or the VM stopped. If no ping answers, it refreshes the status, and if the VM still runs, it sends one notification with a **Restart** button. An `AlertThrottle` of 30 minutes, keyed by kind and profile, stops repeats. A ping that answers resets the no-answer key, so a new failure after a recovery notifies again.
- `syncClock(_:_:)` runs when Docker answers. It measures with `ClockDrift.sample` (`GET /info`, the middle of the request time). A fix is needed when the offset minus the uncertainty is more than 2 seconds. Then it waits 20 seconds for Lima (Lima 2.1 and later set the guest clock every 10 seconds) and measures again. If the clock is still off, it runs `colima ssh --profile P -- sudo -n date -s ±N.NNNsec` through `Shell.run`, with stderr in the output for the log. A set of profiles with a clock fix in flight stops a second fix for the same profile. GNU date applies the amount to the guest clock when it runs, so ssh adds no error. It is not a `colima-ctl.sh` action. It sends a notification only if the last measurement still needs a fix.
- `restartFromAlert(_:)` handles the **Restart** button. It checks, in order: the profile exists (`colima.yaml`, except for `default`, and the profile list), no action runs for it, and its VM runs. It restarts only then. Else it posts a short notice, so `colima start` never makes a new VM or starts a VM that the user stopped. `ColimaModel.alertRestart` holds the rule.
- When Docker answers and the clock check ends, `checkPortsAfterWake(_:)` waits 15 seconds and checks the published ports, see [Network health](#network-health).
- The check uses the Colima sockets, never the proxy sockets, so it never starts a VM.
- The readiness gate of `performWake` uses `SuspendingClock` for its deadline, so a sleep during the gate does not use up the time.

### Login item

The login item is a plain LaunchAgent plist with the label `com.imohitkr.ColimaBar.login` in `~/Library/LaunchAgents`. It has `KeepAlive` for a failed exit, so launchd restarts ColimaBar after a crash. A normal quit is respected.

ColimaBar does not use `SMAppService`. launchd ties an `SMAppService` agent to the code signature, and each ad-hoc build has a new signature. `LoginItem.migrate()` removes the old agent one time.

### Notifications

Notifications go out for failures: a container exits with an error, gets OOM-killed or becomes unhealthy, or an action fails. Exit codes 0, 130, 137 and 143 are a normal stop (`ColimaModel.ignoredExitCodes`). `ContainerAlertGate` holds the rest of the policy. It is pure and takes the time as an argument:

- A `kill` event with signal 1, 2, 3, 9 or 15 marks the container as stopped on purpose for 120 s. `docker stop`, `docker restart`, Compose and the ColimaBar buttons all send it before `die`, and an OOM kill does not. Any other signal gives a 15 s window. A `die` in a window is no crash and is not counted. A `start` ends the window.
- A VM-wide action sends no `kill` for each container. `CtlAction.stopsContainers` makes `executeResult` hold the alerts of the selected profile while it runs and for 30 s after (`QuietWindows`). A profile switch makes a new gate, and the old action does not release it. ColimaBar checks an unhealthy alert from this time again when the time ends.
- `RestartLoopTracker` counts every exit, also code 0, except the ones in a window. The first exit alerts if its code is a crash code. A later exit alerts if its code is a crash code and no crash alert went out since the first exit of the current run of exits (the 5-minute window). The third exit in 5 minutes sends one "keeps restarting" notice. Crash alerts stay silent until 10 minutes pass with no exit, or until a `healthy` event. In a loop, OOM and unhealthy alerts are silent only in the 5 minutes after the last exit. An OOM event with two exits in that window is silent too (`exitCount`): the next `die` sends the loop notice.
- An unhealthy event inside 180 s after a `start` is checked again at the end of the grace. It alerts only if the container is still unhealthy. If the list of containers cannot be read, the check tries once more after 15 s and then alerts without it, but only while the VM runs and the container exists: a stopped VM or a `destroy` ends the check with no alert.
- An optional "Healthy again" notice (`notifyOnRecovery`, not recorded in the dashboard list) follows an unhealthy banner that went out.

A muted Compose project (`Defaults.Key.mutedProjects`, entries `profile/project`, not in the settings file) skips only the banner and the sound: the dashboard list still gets the alert. The list holds at most 200 entries (`MutedProjects.maxCount`). A new mute at the cap does nothing. The gate state is in memory and a profile switch resets it.

Containers with the label `org.testcontainers=true` do not send alerts. Two other notifications go out once: one for each new version, and one the first time the icon hides. After an in-app update, the new version sends one more. A volume backup or restore sends one when it ends or fails. Return Free Space sends one when it ends, with the size of the disk image before and after. The weekly cleanup sends one only when it fails. A compose run sends one only when it fails or reaches its time limit. A third goes out after a good auto-start with a risky Colima or Lima change since the last good start (see the upgrade guard). Its click opens the release notes. `AlertThrottle` allows one banner for each container and alert kind each 10 minutes. A refused or bad link sends one (see Links). It is rate-limited, and it becomes an alert window when notifications are off. The checks after a system sleep send a notification with a **Restart** button (category `PROFILE`) when Docker does not answer or the clock fix fails. The network checks send one with the same button, see [Network health](#network-health). A click on its banner does nothing. The dashboard keeps a list of recent alerts, so nothing is lost when notifications are off.

**Saved logs.** Docker removes an auto-remove container (`docker run --rm`) and its logs right after it dies. While the option is on (`Defaults.Key.keepRemovedLogs`, off by default) and crash alerts are on, `RemovedLogKeeper` does this for the selected profile:

1. On a `start` event, it inspects the container. If `HostConfig.AutoRemove` is true, it opens one log stream (`follow=1`, `tail=100`).
2. The stream thread stores the raw log bytes in a `RemovedLogRing`, at most 500 lines and 128 KB for each container. Nothing parses them yet. The main actor does no work for each line.
3. On `die` with a crash exit code (`ColimaModel.isCrashExit`, the same rule as the alert) or after `oom`, it keeps the lines for 5 minutes. A clean exit, or a `destroy` without a failure, drops them. It closes the stream at most 2 seconds after `die`.
4. "View logs" calls `ColimaModel.openLogs`. `LogStore` inspects the container. If the daemon answers 404, ColimaBar parses the saved bytes, and the window shows the lines with the status "Saved from a removed container" and does not reconnect. Otherwise it shows live logs.

The buffers are not observed. The model publishes only `savedLogIDs`, the set of kept containers, for the alerts list. A profile switch, or turning the option off, drops all buffers.

### Update check

`Updater` asks the GitHub releases API one time each day. It builds the release link from the tag and accepts only release pages of this repository. `ReleaseInfo.parse` reads the answer. It rejects drafts and prereleases, and never uses `html_url` or `browser_download_url`.

### In-app update

`InstallSource.detect` decides what the update button does. The first rule that fits wins: a debug run, a version that is not exactly X.Y.Z (a development build), Homebrew (the Caskroom link points to the bundle, or the Caskroom folder exists and the bundle is `/Applications/ColimaBar.app`), a copy that is not installed (`LoginItem.isInstalled`), a read-only volume, a folder or bundle that the user cannot write (or another owner, or a symlink). Only a copy that passes all rules updates itself (`selfUpdate`). Homebrew shows the `brew upgrade` command. The others open the release page.

The install runs in `Updater+Install`. Any failure before the swap stops it, and nothing in the Applications folder has changed:

1. The user confirms (`UpdateAlert`). The alert says if `gh` can check the attestation. `ColimaModel.updateActivity` and `UpdatePolicy.blocker` decide if a restart is allowed now.
2. `UpdateDownload` downloads `ColimaBar.zip` of the exact tag into `~/.cache/colima-bar/update/<uuid>` (`Paths.updateDir`, mode `0700`). It uses an ephemeral session, follows redirects only to `ReleaseLink.downloadHosts` (`allowsRedirect`), stops when the file passes the size that the API lists, and hashes with CryptoKit while it writes.
3. `UpdateVerifier` compares the size and the digest, runs `AttestationCheck` (`gh attestation verify` with the flags of `install.sh`; it is skipped only if the dialog said that `gh` cannot run it, and it stops the update if the dialog promised it and `gh` fails to run it later; a cancel stops the running tool with SIGTERM through `Shell.run(cancellable: true)`), unpacks with `ditto` (one entry, `ColimaBar.app`, at most 100 MB), runs `codesign --verify --deep --strict` with the requirement `identifier "com.imohitkr.ColimaBar"`, checks the plist (`plistProblem`) and the script, and removes the quarantine flag from the unpacked copy and reads the flags again.
4. `BundleSwap.prepare` copies the app beside the target (`.ColimaBar-update.app`) if the unpacked copy is on another volume. `BundleSwap.commit` swaps the new and the old bundle with `renamex_np(RENAME_SWAP)` (two renames if the file system cannot swap), checks the version on disk, swaps back if it is wrong, and moves the old bundle to `update/previous` (across volumes it copies it, or gives it the hidden name `.ColimaBar-old.app`). If the old bundle cannot go back, `commit` throws `rollbackFailed(path)`, and the work folder stays until the path is gone (`Defaults.Key.recoveryPath`). After any other failure, a cancel or a time-out, `BundleSwap.discard` removes the staged copy. `LoginItem.isInstalled` rejects names that start with a dot, so a staged or old copy never counts as installed. The swap is the only step that touches the Applications folder. It renames; it never writes into the running bundle, so the running binary keeps its inode.
5. The last busy check, `Defaults.Key.installedVersion`, the swap and the restart (`relaunchIfUpdated(reveal: false)`) run on the main actor with no `await` between them. The agent restarts with `exit(EX_TEMPFAIL)` and KeepAlive. A copy that was started by hand opens a new instance with `--replace` and quits when that call ends (so the "no `await`" claim holds only for the agent). While the phase is `installing`, `ColimaModel.run` refuses VM actions, and a proxy wake waits for up to 10 seconds. If the new instance cannot start, `Updater.relaunchDidFail` shows a notice and drops the offer. On shutdown, the proxy sockets become symlinks to the Colima sockets, so clients keep working. The new copy binds the sockets again, and the readiness gate is unchanged. During about 2 seconds, a docker command does not start a stopped VM, and open connections close.

At launch, `Updater.finishInstall` shows one notification if `installedVersion` is the running version. In every case it removes the key and the update folder, which holds the previous version. A failed check or swap (`UpdateError.usesReleasePageAfter`) changes the button to the release page until the next launch. A network error, a cancel and busy work keep the install button.

A debug run never updates: `detect` gives `debugRun`, and `install()` checks `isDebugRun`. A test build (`COLIMABAR_UPDATE_TEST=1 ./build.sh`) compiles `UpdateTestHooks`. It reads `COLIMABAR_UPDATE_BASE=http://127.0.0.1:PORT` and moves the API and the download to a local server. A release build must not have it. CI checks the binary for that name. See [CONTRIBUTING.md](CONTRIBUTING.md#test-build-for-the-in-app-update) and [SECURITY.md](SECURITY.md).

### Performance and limits

When the dashboard is closed, the app idles at about 0% CPU. These limits keep memory and file use low:

| Limit | Value | Where |
|---|---|---|
| Open file limit | 8192 (launchd starts apps with 256) | `FileLimit`, login item plist |
| Lines in a log window | 20,000 lines and 32 MB of text | `LogLimits` |
| Rendered log lines | the newest 2,000; copy and filter use all lines | `LogTail` |
| Saved logs of removed containers | 500 lines and 128 KB of raw log data for each container, 50 containers (about 6.4 MB), 5 minutes after a failure | `RemovedLogKeeper` |
| Proxy request head | 64 KB, then HTTP 431 | `SocketProxy.maxHead` |
| Proxy copy buffer | 16 KB for each direction | `SocketProxy.bufferSize` |
| Domain proxy request head | 64 KB, then HTTP 431 | `HTTPHead.maxBytes` |
| Domain proxy head timeout | 10 s, then HTTP 408 | `DomainProxy.Limits.headTimeout` |
| Domain proxy sessions | 512, then HTTP 503 | `DomainProxy.Limits.maxSessions` |
| Domain proxy upstream connect (TLS handshake included) | 5 s, then HTTP 502 | `DomainProxy.Limits.connectTimeout` |
| Domain HTTPS leaves | One for each route, and 256 cached at most (the least recently used goes first) | `LeafCache` |
| Idle client while the VM is down | closed after 5 minutes | `SocketProxy.idleTimeout` |
| `ctl.log` | starts again after 1 MB | `Shell` |

Live stats stream only while a dashboard is on screen. Saved-log streams open only while the option is on, one for each running auto-remove container. `/system/df` runs only for the tabs and the Cleanup page that show it. The log listing of the Cleanup page runs only while the page shows, at most once each 60 s. Graphs use SwiftUI `Shape`, not Swift Charts, because Swift Charts uses a lot of graphics memory.

### Container domains

The setting `domains` turns on a proxy that opens containers at `.localhost` names. A browser resolves `*.localhost` to the Mac itself, so the feature needs no DNS setup.

- **Routes.** `refreshContainers()` gives the raw `[APIContainer]` list to `updateDomainRoutes`. It makes `DomainCandidate` values and calls `DomainRoutes.build`. The result goes to the UI (`domainRoutes`, set only when it changes) and to the proxy (`domainProxy.routes`). The model rebuilds the routes when the list, the VM state or the setting changes.
- **Names.** A Compose service is `SERVICE.PROJECT`. Another container is its name. Replicas get `SERVICE-N.PROJECT`. Labels add names. The container port comes from the label, else the first published port of `DomainPorts.preferred`, else the lowest web port. A collision goes first to a name from a label, then to the derived primary name, then to the plain name of the lowest replica, then to the older container. The container port comes from the label, unless it is a non-web port (`PortLink.nonWebPorts`) or not a port: then a note shows and the first rule applies. Notes (`DomainRoutes.Note`) tell the user about a lost name, a bad label or a dropped entry. The row shows all of them. A replica name is `SERVICE-N` cut to 63 characters.
- **Resolve.** The Host must end in an active suffix. Else the answer is `foreign` and the page shows no list. If the VM does not run, the answer is a 503 page. A request never starts a VM. Else the longest known parent name wins.
- **Proxy.** `DomainProxy` binds `127.0.0.1` and `::1` on port 80, else 8080. Before it binds, it skips a port that a running container publishes or that answers a connect. `queue` runs every Network.framework handler. `table` has its own lock, and a session reads one snapshot of it. A session reads the head, connects to `127.0.0.1:<published host port>` (with TLS for container ports 443 and 8443, with any certificate) and splices both directions with backpressure. A route that was published on `::1` only has `ipv6Only` and connects to `::1`. The proxy routes by the Host of the first request on a connection only, and it has no idle timeout after the head. A route to its own port gets a 502 page (`DomainPage.Kind.selfLoop`), and a TLS handshake has the same time limit as the connect. An upstream error ends the session at once, so the client sees a reset. After an error page, `FinalPage` half-closes the write side and reads for up to 1 s, so that the client does not lose the page to a reset. `start` waits until the old listeners are cancelled before it probes ports. This includes the listeners of an earlier `stop()` and of a bind that was still running (the next `start` or `stop()` aborts it). The constructor accepts loopback addresses only. A request from a listener of an older start, or after `stop()`, is cancelled. `DomainProxying` is the seam that the model tests use.
- **Lifecycle.** The proxy starts at launch and when the setting turns on. It stops when the setting turns off and at quit. `domainStartToken` drops the result of an older start. The start order is port 80, then (at launch only) a wait of 1 s and port 80 again, then port 8080. A port that any running container publishes (also an internal or a testcontainers one) is no candidate. If a container publishes the port of the proxy, now or while the proxy starts, the model moves the proxy at most once in 30 s (`DomainTimings.rebindGap`). A move inside the gap runs when the gap ends. A proxy on 8080 goes back to 80 when 80 is not published and a probe finds it free: the model checks after a route rebuild and after a wake, within the same gap. A failed proxy starts again when the set of published ports changes, after a wake, and on a timer: 5 s, 15 s, 60 s, then every 5 min (`DomainTimings.failureDelay`, `domainRetry`). A failure callback of an older start is ignored (`domainStartToken`). `shutdown()` invalidates the token and cancels the timers. The heartbeat (`domainsHeartbeat`) moves a proxy on the fallback port back to 80 when a probe finds it free, at most once in a rebind gap. After a wake, the model starts the proxy if it does not listen. `domainURL` gives a link only while the proxy runs (a debug run gives port 80). `DomainPortClaims` keeps the host ports of every container of the profile by container ID, from the `all=1` list. A stopped container keeps its last ports, because the list gives none for it. A container that leaves the list gives its ports back. A stopped VM keeps the claims, and a profile switch clears them. The start and the move back skip every claimed port, running or stopped. Lima forwards a port once at the container start and never tries again. So, if a running container publishes the port that the proxy holds (a conflict, not a skip at the start), the model adds a `DomainRestartHint` and one entry to the alerts list. The hint ends when the container stops or leaves the list. The HTTPS listener follows the same rules: its start and its move back skip every claimed port (`domainBlockedPorts`), and a conflict on its port adds the same hint.
- **Debug runs.** A model in a test process gets an inert proxy, inert TLS services and an empty settings store unless the test passes its own (`TestProcess`, `InertDomainProxy`, `InertDomainTLS`), so no test binds a port, makes a CA, touches a keychain or a trust setting, or changes the saved setting. A debug run starts no listener and never writes the setting. It ignores the saved setting. With `COLIMABAR_DOMAINS=1` it computes the routes, so a screenshot shows the links.

### Links

`colimabar://open`, `doctor`, `start`, `stop` and `restart` reach the app as an Apple event (`kAEGetURL`). `AppDelegate.installLinkHandler()` installs the handler first in `applicationWillFinishLaunching`, so a link that launched the app is kept. The handler only queues the text in `LinkInbox`. `applicationDidFinishLaunching` opens the inbox. The inbox holds at most 4 links, drops the same text within 2 seconds, drops every link while a question is open, and gives one link at a time.

`AppLink.parse` is pure. It accepts only the five routes and, for `start`, `stop` and `restart`, one `profile` parameter that passes `ProfileName.isValid`. A VM link first refreshes the status. Then `AppLinkPolicy.decide` checks, in order: an update restart, Colima missing, a failed list, an unknown profile (a link never creates a VM), a running action, and the VM state (no-op or refusal). While `askBeforeLinks` is on, `LinkAlert` asks first, and the policy runs again after the answer. The profile reaches the script only through `model.run`, as `COLIMABAR_PROFILE`.

If LaunchServices starts a second copy for a link, that copy forwards the links to the running copy (`NSWorkspace.open`). If the request fails or takes more than 2 seconds, it reopens the running copy. Links that arrive while it waits go in the next round. A refused or bad link shows as a notification, or as an alert window if notifications are off. Link messages are limited to one for each link and kind per minute, and 5 per minute in all. If the login item is on, it writes `linkHandoff` for the login agent before `kickstart()`, and the agent takes it at launch. A non-debug copy in an Applications folder registers the scheme with `LSRegisterURL`, off the main actor.

`revealDashboard()` opens the dashboard for a reopen event, `--reveal`, a link and the Doctor menu item. It opens the popover only when `StatusItemPlacement.canAnchor` is true (the icon is on a screen and not under the camera housing). Else it opens the window. If the popover still opens off screen, it opens the window.

### Command line

`colimabar` is a short bash wrapper (`scripts/colimabar.sh`) in `ColimaBar.app/Contents/Resources/bin`. It finds the app through its own links (`readlink -f`) and runs `Contents/MacOS/ColimaBar --cli ARGS`. A link to the binary would not work: the system finds the bundle from the path of the executable, and `Bundle.main` and `UserDefaults.standard` must be the ones of the app. The first line of `AppDelegate.main()` checks `isCommandLine` and calls `CLIRunner.main(_:)`, before `NSApplication.shared` exists. So the command has no Dock icon and no status item, and it never reaches `ensureSingleSupervisedInstance` or the login item. A second target or a script would need a library split of the app, a nested signature or a second copy of Doctor and `Redactor`. If `Bundle.main` is not ColimaBar, the command exits with 1.

The command has no control socket and sends no Apple event. It reads facts from these sources:

| Fact | Source |
|---|---|
| State, runtime, CPUs, memory, disk of the VM | `colima list -j`, at the moment of the call |
| Action in progress | The busy marker, read only. The command never removes a stale one. |
| Selected profile, auto-start and auto-stop settings | The `UserDefaults` of the app |
| App running, app version, auto-stop time of each profile | `~/.cache/colima-bar/app-status.json` |
| Socket kind | One `lstat` of the socket path, and whether the app runs |
| Docker context | `Routing.currentContext()` |
| Doctor, diagnostics | The command runs them with a read-only `ColimaModel` |

`AppStatus` is the status file: `{"format":1,"pid":N,"version":"X","autoStopAt":{"default":"2026-10-19T09:12:00Z"}}`, mode `0600` in the folder with mode `0700`. A normal run writes it (`publishAppStatus()`) when it starts, when a profile gets or loses an auto-stop time, when a time moves by 1 second or more, and when the file is gone. The write is a temporary file made with `O_CREAT|O_EXCL|O_NOFOLLOW`, then `rename`. `shutdown()` removes the file only if it holds its own PID. The file is stale on the rule of the busy marker (`BusyMarker.isStale`): the PID must belong to a process that started before the file was written. A stale, unreadable or too big file means "the app does not run". A debug run and the command never write it.

`ColimaModel(profile:readOnly:)` is the model of `doctor` and `diagnostics`. A read-only model counts as a debug run (`isDebug`), and the command never calls `start()`. So it starts no proxy, changes no route, context or setting, and makes no Doctor fix. The fallback to the `default` profile in `refreshStatus()` also needs `!isDebug`, or a debug run would save `default` as the profile. `ColimaModel.notify` does nothing in the command: the command never touches `Notifier`. The diagnostics header shows "(command line)" (`DiagnosticsBundle.render(runNote:)`).

`start`, `stop` and `restart` run `colima-ctl.sh` as the app does (`COLIMABAR_PROFILE`, `COLIMABAR_APP=1`). First they run `colima list -j`. A profile other than `default` that is not listed gives exit 1, so a typo never creates a VM. While a busy marker or a `colima start` holds the profile, the command waits (1 s steps, 15 minutes at most). It asks no question, sets no `COLIMABAR_UPGRADE_NOTE`, uses no link and records no good start. After a good `start` or `restart` of a docker profile it waits for `ReadinessGate` on the socket of Colima. SIGINT and SIGTERM cancel the task. The task sends SIGTERM to the script, which removes its lock and busy marker. The exit codes are in `CLIExit`: 0 done, 1 failed, 2 usage, 3 lock held (the script exited with 2), 130 and 143 for the signals.

The JSON of `status` and `doctor` has `schemaVersion` 1. Every key is always there, with `null` when it has no value. A new key keeps the version. A rename, a removal or a change of a type raises it. The text can change. The output has no names or counts of containers, images, volumes or networks, and the Doctor JSON has no registry host. `--profile` passes `ProfileName.isValid` and reaches the script only through the environment.

`open` calls `NSWorkspace.openApplication` for the bundle of the command. If the status file showed no app, it waits up to 10 s for the app and opens once more, so the dashboard shows.

### Keyboard shortcut

`HotKey.shared` registers one global shortcut with Carbon `RegisterEventHotKey` and `InstallEventHandler` on the application event target. It needs no permission. An event tap or a global monitor would need Input Monitoring or Accessibility.

- **Exclusive.** The registration uses `kEventHotKeyExclusive`. macOS refuses a key that another process holds with `eventHotKeyExistsErr` (-9878), shown as "Another app uses this shortcut". A holder that did not register exclusively keeps no key while ColimaBar runs. Before `set` registers, it checks `CopySymbolicHotKeys` (`KeyCombo.isReserved`), so the recorder also refuses an enabled macOS shortcut.
- **Rules.** `KeyCombo.problem` needs two or more of ⌘ ⌃ ⌥, or one of them with a function key. ⇧ does not count.
- **Storage.** `Defaults.Key.hotKey` holds the spec string, for example `control+option+command+C`. The settings file holds the same string, and an empty string means none. `uninstall.sh` removes the key with the other defaults.
- **Threading.** The C handler is a file-scope function. Carbon calls it on the main thread. It checks the signature and gives the press to the main queue, and `HotKey.pressed()` runs after the handler returns. `toggleDashboard()` then picks an action (`AppDelegate.shortcutAction`) and calls `revealDashboard()` to open.
- **Launch.** `start(debug:)` runs after `ensureSingleSupervisedInstance()`, so only the live copy registers. A copy that hands over or reopens the old copy exits first. If the key is still held, `start` tries again after 1 s and 3 s. `applicationWillTerminate` calls `stop()`.
- **Recording.** `ShortcutRecording` pauses the hot key (`pause()`), so the keys reach its local event monitor. It resumes the hot key when it ends, loses the key window or the row disappears. `set(_:)` saves the shortcut only after the registration succeeds, and a failed change keeps the old one.
- **Debug runs and the command.** A debug run reads the stored shortcut for display and export. It registers nothing, and `set` does nothing. The command never touches `HotKey`: the settings snapshot reads the stored string from `Defaults`.

### Local certificate authority

The setting `domainsHTTPS` (not in the settings file) adds an HTTPS listener to the proxy. It needs `domains`.

- **CA.** `LocalCA.create` makes a P-256 key (never permanent) and a certificate for 10 years: `CA:TRUE` with path length 0, key usage `keyCertSign` and `cRLSign`, extended key usage `serverAuth`, and a critical NameConstraints extension. It permits the DNS names of `activeDomainSuffixes` (now `localhost`) and excludes `0.0.0.0/0` and `::/0`. `X509Builder` writes the DER by hand, and the tests check it through `SecCertificateCreateWithData` and `SecTrust` with the CA as the only anchor.
- **Storage.** `LocalCAStore` keeps `ca.der` (0600), `ca.pem` (0644, for `NODE_EXTRA_CA_CERTS`) and `ca-key.raw` (0600, `04 || X || Y || D`) in `~/Library/Application Support/ColimaBar/domains` (0700, no backup). `save` writes `domains.new` and swaps it in with one rename, so a crash never leaves a certificate with the key of another CA. `load` refuses a symlink, another owner or a wrong mode, and `LocalCA.restore` checks the certificate (self-signed, CA flag, issuer is subject, inside its dates) and that the key signs a nonce which the certificate verifies. The key is never a keychain item.
- **Trust.** `TrustStore.install` adds only the certificate to the login keychain and sets user trust settings for the SSL policy. It shows one macOS dialog. `remove` removes the trust setting and then the certificate. A cancel keeps the certificate, so the user can delete it in Keychain Access. `removeLabelled` does the same for the certificates labelled "ColimaBar Local CA", when the files are gone. No `kSecUseDataProtectionKeychain`: a Mac app without an entitlement gets -34018.
- **Flows.** `setHTTPS(true)` closes the popover, makes or loads the CA, calls `TrustStore.install` and starts the listener. A cancel deletes the files. A marker in the settings (`domainsHTTPSPending`) stays from before the dialog until its outcome. The next launch cleans up once, inside `httpsSetupTask`, and never calls `uninstall`: it keeps a CA that has trust settings, and else deletes the keychain certificate (no dialog) and the files. A second marker (`domainsHTTPSRemoving`) stands while the removal dialog shows. If the app ended then, the next launch shows the note about the certificate "ColimaBar Local CA" and a **Delete Certificate…** button. The user clicks it. Nothing runs by itself. `DomainRoutes.rememberedNames` keeps the route names while the VM stops (same profile and suffixes, at most 256), so the leaf cache and the certificate of the fallback mode still cover them and the 503 page opens without a warning. A conflict with a container port shows `settingUp` at once, and the move back to port 443 keeps the status. In the fallback mode, each listener has a new certificate (`multiSANEpoch`), and the old one goes after the new listener runs. `setHTTPS(false)` works with the master switch off. It stops the listener, deletes the key file before the dialog, and then removes the trust and the certificate (or the labelled certificates, when the files are gone). A launch with the setting on loads the CA and shows no dialog: a missing trust is the phase `untrusted`, and a missing file is `failed`. A CA that does not permit every active suffix starts no listener: the phase is `untrusted` without a port, and **Trust Again…** replaces the CA (macOS removes the old one, then trusts a new one). The model checks the trust again after a wake and at most once a minute in the heartbeat. The master switch off stops the listener and keeps the CA.
- **Identity.** Network.framework wants a `SecIdentity`. `PKCS12.identity` builds a PKCS#12 blob in memory from the certificate and the P-256 key of a leaf (`04 || X || Y || D` from `SecKeyCopyExternalRepresentation`, written as PKCS#8 with `DER`). The key bag is encrypted with PBES2 (PBKDF2 with HMAC-SHA256 and AES-256-CBC) and the file has the RFC 7292 MAC (HMAC-SHA256), both with a random password that stays in memory, because the importer refuses a file without them. `SecPKCS12Import` with `kSecImportToMemoryOnly` (macOS 15) returns the identity and touches no keychain. `TLSIdentities.selfTest` mints a leaf, makes the identity, and checks the private key and a signature. `TLSIdentities.cleanStale` deletes the `tls-PID.keychain-db` files that older versions left in `~/Library/Caches/com.imohitkr.ColimaBar/tls`, at launch.
- **Leaves.** The challenge block of `DomainTLSServer` picks the identity by SNI value in `LeafCache` on a queue of its own. `LeafCache.mintName` accepts only a name that the route table resolves (a route name or a subdomain of one) and the self-test name of each suffix. Every other name gets the `localhost` leaf, which is never made again, so a page cannot make the cache mint without end. A leaf lives 30 days, stays in memory and is made again when less than 1 day is left. The cache holds 256 leaves. The least recently used one goes first and is freed. ALPN is `http/1.1` only.
- **Self-test and fallback.** After the listener starts, `DomainTLSServer.selfTest` connects with the SNI value `colimabar-selftest.localhost` and the CA as the only anchor, and expects an HTTP answer. If it fails, the listener restarts in `multiSAN` mode with one certificate for all route names, and `syncMultiSANLeaf` makes a new one 2 s after a route change. The fallback is best effort: a browser may not accept `*.localhost`. A timer makes a new certificate after 29 days. The self-test uses one name under each active suffix. Two failures stop HTTPS.
- **Ports.** The listener tries 443 and then 8443 with the same rules as HTTP: a published port is no candidate, a conflict moves it once in 30 s, a launch tries 443 twice, 8443 goes back to 443, and a failure retries after 5 s, 15 s, 60 s and then every 5 min. The two listeners have their own state in `DomainProxy` (`Front`), so one restarts without the other.
- **Links.** `domainURL` uses `https` and the HTTPS port only while the phase is `running`. In the phase `untrusted` links stay HTTP.

### Custom suffix and DNS

The setting `domainSuffix` (not in the settings file; `domainDNSPort` is its machine state) adds a second suffix to `activeDomainSuffixes`. It needs `domains`.

- **Suffix.** `DomainSuffix` (pure) checks the value: `test`, or one or two labels before `test`, `internal` or `home.arpa` (at most 4 labels and 100 bytes in all), never `localhost` or `local`. The default is `colima.internal`. A stored value that fails the check is ignored at launch.
- **DNS.** `DNSMessage` (pure) answers one question inside the zone: `A` with 127.0.0.1, `AAAA` with ::1, no answer for other types, REFUSED without AA outside the zone (or with an empty zone, or for a class other than IN and ANY), FORMERR, NOTIMP or REFUSED for bad packets, no answer to a short, long or response packet. It never follows a compression pointer and ignores an EDNS record. `DNSResponder` serves it over UDP on `127.0.0.1` only, on a port from 20000 to 32767 (`pickDNSPort`). A flow for each source endpoint reads message after message (a resolver sends A and AAAA from one socket), up to 64 messages, and closes after 5 s without one. There are at most 256 flows. The model reaches it through `DNSServing`.
- **Resolver file.** `ResolverFile` builds `/etc/resolver/SUFFIX`: a marker line, `nameserver 127.0.0.1`, `port N`. `ResolverFile.shellCommand` is the /bin/sh text that installs the new file through a temporary file `.SUFFIX.colimabar-tmp` and `mv` (exit 3 and the token `colimabar-foreign` for a file without the marker or a link), and only then removes the old file (only if it has the marker and is a regular file). A trap removes the temporary file when a step fails. The text gets only a suffix that passed `DomainSuffix`, a fixed folder, the marker and an integer, each through `shellQuote`. `appleScript` escapes it for `do shell script … with administrator privileges`. `ResolverInstaller.apply` runs it through `osascript` (one prompt) with an injected runner. The cancel is the error `(-128)` only. `precheck`, `inspect` and `port` read the file without root.
- **Flows.** `applySuffix` checks the file for a foreign owner (no prompt then), picks or reuses a port, closes the popover, writes the file (new first, then old, in one prompt), starts the server and asks the system resolver for `colimabar-selftest.SUFFIX` (`verifyResolver`: `.running` or `.notUsedYet`, with new checks after `DomainTimings.dnsRecheck` while it stays `.notUsedYet`). `removeSuffix` removes the file, also with the master switch off. `repairDNS` picks a new port and writes the file again. A launch starts the server on the stored port if the file is ours and names that port, else the phase is `.failed` with **Repair…**. A launch and a wake check the system resolver again. The master switch off stops the server and keeps the file. It never changes the phase `.applying`, and the switch is off in the UI while a write runs.
- **CA.** With HTTPS on, a change of the suffixes calls `replaceCAForSuffixes()`, which uses the replace flow of the HTTPS section (the same as **Trust Again…**). A CA that lacks a name stops the HTTPS listener at once (`runHTTPS` gives `.untrusted` with `needsNewCAText`), then `reissueCA(old:)` removes the old CA and makes and trusts a new one. A CA that permits a name that is gone is replaced the same way, and a cancel leaves HTTPS running with the old CA. It needs the master switch on. Links use the custom suffix over HTTPS only while `tlsCA` covers it (`primaryDomainSuffix`).

### VM type change

Colima reads `vmType`, `mountType`, `arch` and `runtime` only when it creates the VM, and it discards a new value for an existing VM (`setFixedConfigs` in `cmd/start.go`). Thus **Change and Recreate…** (`VMTypeSection`, in the VM settings page) deletes the VM and creates it again. The pick is no part of `VMSettingsChange`, so **Apply** ignores it. `VMSettingsCheck.recreateProblems` gives the red problems.

- **Data disk.** `colima delete` without `--data` keeps the Lima data disk (`_lima/_disks/colima[-PROFILE]`) and its entry in `_store/*.json`. The next start finds the disk and mounts it: `/var/lib/docker`, containerd, k3s and the rest stay. `VMRecreatePlan.dataDiskKept` and `data_disk_kept` in the script use the same rule: the disk folder exists and the store has `"disk_formatted": true`. Without a data disk (a profile from before Colima 0.7), the delete removes all data, and the warning says so.
- **Flow.** `VMRecreateFlow.run` backs up the volumes (`VolumeBackupBatch` through `performBackup`), saves the images (`ImageArchiveRunner.save`: `GET /images/get` into a private file with `TarScanner(names: .any)` and a SHA-256), runs `vm-recreate`, waits for Docker (`ReadinessGate`, 120 s) and restores what is missing. A failure or a cancel before the script stops the flow: the VM stays as it is. `ColimaModel` holds `actionsInFlight` of the profile for the whole run, so auto-stop, the weekly cleanup and the checks after sleep stay away.
- **Idempotent restore.** The restore takes only the volumes that `lookup` reports as missing (`VolumeRestoreFlow.run` with `isNew: true`). It loads `images.tar` only if a saved reference answers 404. After a kept data disk, both steps do nothing. `resume` runs only this part.
- **Journal.** `~/.cache/colima-bar/recreate.PROFILE.json` (mode 0600, `PrivateFileWriter(replace: true)`) has the types, the backup folder, the file names, the SHA-256 of `images.tar` and the phase: `backup` (nothing changed), `recreate` (the script runs) and `restore`. A copy goes to `recreate.json` in the backup folder. `VMRecreateJournal.load` checks the format, the version, the profile name and that a file name has no path. At launch and after each `colima list`, `ColimaModel.loadRecreateJournals` reads the journals and `VMRecreateJournal.recovery` says what the notice shows (`VMRecreateNotice`), from the phase and the types in `colima.yaml`. A profile with a busy marker or a running change has no notice. A debug run only reads.
- **Backup folder.** `ColimaBar-PROFILE-YYYYMMDD-HHMMSS`, made with `mkdir` (mode 0700, it fails if the name exists). Files are 0600. The alert checks the free space: the chosen size, 10% more and 2 GiB.
- **Sleep, quit and profile switch.** A transfer that breaks after a sleep fails its step. Before the script, nothing changed. After it, the journal stays at `restore`. A VM stop or a profile switch cancels the runners (`clearVMData`), and the flow stops before its next restore step. If ColimaBar quits, the script goes on, and the next launch shows the notice.
- **Progress.** `VMRecreateProgress` mirrors the volume transfer (`setVolumeTransfer`) and the image bytes. **Cancel** works only in steps that can stop (`canCancel`).

### Debug runs

`--snapshot`, `--popover`, `--notify-test`, `--diagnostics` and `--cli` start a debug run. A debug run ignores links. It does not change the proxy sockets, the docker routes and contexts or the login item. It registers no keyboard shortcut. It starts no domain proxy, runs no DNS server, writes no resolver file, makes no CA and changes no keychain or trust setting. It also skips system sleep, power and network changes and auto-stop. It runs the Doctor checks (they only read: the network checks connect to ports on the Mac without data, run `colima ssh` and look up a name), but makes no Doctor fix and writes no VM settings. It may write the diagnostics file that the user chose. It writes no upgrade record. It runs no docker compose, opens no debug shell, makes no volume backup or restore, removes no helper container, trims no disk, empties no log and runs no weekly cleanup. Thus it can run next to the installed app. [CONTRIBUTING.md](CONTRIBUTING.md#debug-flags) lists the flags.

## Invariants

Do not break these rules.

- **Fixed popover size.** The popover is 480 x 640 points (`AppDelegate.popoverSize`). In `ColimaModel`, assign a property only when its value changes. Otherwise the popover jitters and SwiftUI redraws too much.
- **No dialog behind the popover.** Call `model.dismissPopover()` before an alert or a file panel opens from the popover. A `colima-ctl.sh` action that asks with a dialog has `CtlAction.showsDialog(running:)`, and `run()` closes the popover for it. Some actions ask only while the VM runs. A test checks the list for a running VM against the script. The upgrade dialog is the exception to the list: `execute()` calls `dismissPopover()` itself when it passes an upgrade note. The HTTPS flows (turn on, turn off, Trust Again, Delete Certificate) also call `model.restoreDashboard()` when the dialog ends with any outcome, if a dashboard was open. AppDelegate shows the window or the popover again, key and focused.
- **Proxy sockets.** The stable socket is `~/.cache/colima-bar/docker.sock` (`Paths.proxySocket`). The profile sockets are `~/.cache/colima-bar/profiles/PROFILE.sock` (`Paths.profileSocket`). Each socket has mode `0600`. Their folders have mode `0700`. Do not change the paths or relax the modes.
- **Quit behavior.** On quit, or when auto-start is off, the stable socket path becomes a symlink to the Colima socket of the selected profile, and each profile socket path a symlink to the Colima socket of its profile (`SocketProxy.stop()`). Docker clients must keep working without ColimaBar.
- **Docker contexts.** ColimaBar creates, updates and removes only the `colimabar` context and the `colimabar-PROFILE` contexts whose description starts with "ColimaBar". It never changes other contexts.
- **`colima-ctl.sh`.** The app bundle contains it in `Contents/Resources`. Exit code 0 means done. Exit code 1 means failed (the script already notified the user). Exit code 2 means cancelled, or another VM action holds the lock. ColimaBar shows nothing for 2.
- **Login item.** It is a plain LaunchAgent plist with the label `com.imohitkr.ColimaBar.login` in `~/Library/LaunchAgents`. Do not use `SMAppService`. launchd ties an `SMAppService` agent to the code signature, and each ad-hoc build has a new signature. `LoginItem.migrate()` removes the old `SMAppService` agent.
- **Log `since`.** The Docker logs `since` parameter must be UNIX seconds with nine digits of nanoseconds (`sec.nanos`). See `LogStore.sinceParam`.
- **Readiness gate after a wake.** An open socket does not mean that the Docker daemon is ready. `wakeForProxy()` waits for `colima start` to exit, then for several successful `/images/json` probes in a row (`ReadinessGate`, also used by `colimabar start`). During a wake of profile P, every proxy whose upstream is P holds its requests until the shared wake ends (`SocketProxy.holdForWake`, set by `syncWakeHolds()`). These are the stable socket when P is selected, and the profile socket of P. While a wake runs, `connectIfAwake()` returns `.down`, so no request is spliced before the gate passes.
- **Replace the bundle only by rename.** An in-app update swaps the whole bundle with `renamex_np` (`BundleSwap`). It never writes into the running bundle, and it changes nothing in the Applications folder before the download passes every check.
- **Domain proxy.** It binds only `127.0.0.1` and `::1`. Its upstream is only `127.0.0.1` (or `::1` for a port that is published there only) and a published host port from the Docker list. It never starts a VM. It stops at quit and when the setting is off.
- **Local CA.** Its certificate permits only DNS names under the active suffixes and excludes every IP address. Its key exists only in memory and in a 0600 file in a 0700 folder, never in a keychain. The leaves and their identities stay in memory, with no keychain. The launch deletes the temporary keychain files of older versions. A macOS dialog follows a click only, never a launch, and the popover closes before it. Turning HTTPS off deletes the key file and asks macOS to remove the certificate and its trust setting. A debug run and a test process never make a CA, never bind 443 or 8443 and never touch a keychain or a trust setting: tests use `DomainTLSServicing` fakes.
- **Resolver file.** ColimaBar writes and removes `/etc/resolver/SUFFIX` only through `ResolverInstaller`, with the marker check in the root shell. The root shell gets only validated values. The DNS server binds `127.0.0.1` only and answers only inside the zone. A debug run and a test process write no resolver file, run no `osascript` and run no DNS server.
- **Links.** A link never returns data, writes a file or reaches a shell. Its profile must pass `ProfileName.isValid` and be in a fresh `colima list`. VM links ask while `askBeforeLinks` is on. A debug run ignores links.
- **Command line.** `--cli` never creates `NSApplication`. The command never writes a setting and never changes the system, except through `colima-ctl.sh` (`start`, `stop`, `restart`), the file that the user names (`diagnostics`) and `NSWorkspace.openApplication` (`open`). It never overwrites a file. Only a normal run writes `app-status.json`. The JSON keys of `status` and `doctor` are a contract.
- **Debug runs.** `--snapshot`, `--popover`, `--notify-test` and `--diagnostics` set `AppDelegate.isDebugRun`. The `colimabar` command (`--cli`) is a debug run too. A debug run must not change the proxy sockets, the docker routes and contexts or the login item. It does not back up or restore volumes, makes no VM type change, does not remove helper containers, does not trim the disk, empty a log or run the weekly cleanup. It registers no keyboard shortcut. It starts no domain proxy, runs no DNS server, writes no resolver file. It never downloads or installs an update. It may write only the chosen diagnostics file. It writes and prunes no record of good starts. It does not observe system sleep, power or network changes, it does not auto-stop a VM, and it makes no Doctor fix or repair.

## Testing

Tests use Swift Testing. Logic lives in small static functions, so tests can call it without a VM. `Tests/ColimaBarTests/TestSupport/` has shared fakes, for example `FakeDaemon`. Automated runs never start or stop the user's Colima VM.

`Tests/ColimaBarTests/Scripts/` tests the scripts in `scripts/`. `ScriptSandbox` runs a copy of a script in a temporary HOME, with stub `osascript` (`STUB_OSASCRIPT_OUT` is the button that it answers, `STUB_OSASCRIPT_ERR` the error text), `open` (it logs and opens nothing), `colima`, `docker`, `kubectl`, `pgrep` and `ps` first on its PATH. The stub `ps` answers `-o command=` and `-o etime=` for a PID from a table (`stubProcesses`), so the owner checks of the lock, the busy marker and the pid files of Lima run without real processes. Thus no dialog reaches the screen, and no VM or docker context changes. The uninstall and install tests source only the helper functions of `uninstall.sh` and `install.sh`. `CLIWrapperScriptTests` runs `colimabar.sh` in a fake bundle. The `CLI` tests use pure inputs, so no test runs `colima`, starts a VM or reads the real cache folder.
